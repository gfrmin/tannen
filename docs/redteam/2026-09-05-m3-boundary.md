## RT-M3-01 — A `DeltaNode`'s descriptor names its code by string, so the trace serves the answer to a different computation. **Critical.**

`tannen.incremental` gives user code a name and puts the **name** in the descriptor:

```python
PREDICATES: dict[str, Callable[[Mapping[str, Any]], bool]] = {}        # incremental.py:89
...
self.descriptor = content_address({                                    # incremental.py:293
    "tannen": DELTA_OP_TAG, "operator": operator,
    "params": declared,                                                # {"predicate_id": "risk-ok"}
    "replay": self.replay,
})
```

`declared` carries the string `"risk-ok"`. The predicate itself — the thing that decides which
rows come out — is in a module-level dict and is addressed by nothing.

`advance` then derives the step identity from that descriptor and consults the trace:

```python
step_id = derivation_id(node.descriptor, inputs)                       # incremental.py:441
recorded = traces.lookup(step_id)                                      # incremental.py:443
```

**Reproduction.** Two processes over one store and one trace directory, differing only in what
is registered under the name:

```
=== SESSION 1: honest predicate (x < 100), records the trace ===
[1] node.descriptor = sha256:a45b5ea1fe8759f0c5e7b30bcfc3089432f87481a92fbfdc62c41e50cc1d0be7
[1] step_id  = sha256:f0276065c8d0ed93c1600c54be671aed9c2038892528963f026147619d4169ad
[1] rebuilt  = True
[1] rows out = [(('k', 1), ('x', 5))]

=== SESSION 2: HOSTILE predicate (always true), same name ===
[2] node.descriptor = sha256:a45b5ea1fe8759f0c5e7b30bcfc3089432f87481a92fbfdc62c41e50cc1d0be7
[2] step_id  = sha256:f0276065c8d0ed93c1600c54be671aed9c2038892528963f026147619d4169ad
[2] rebuilt  = False
[2] rows out = [(('k', 1), ('x', 5))]

=== CONTROL: session 2's predicate with a FRESH trace store ===
[2] rebuilt  = True
[2] rows out = [(('k', 1), ('x', 5)), (('k', 2), ('x', 500))]
```

The control is the point: session 2's predicate genuinely returns **both** rows. Against the
shared trace it returns one, and `rebuilt=False` presents that as a legitimate cache hit.
`TraceIntegrityError` — which `advance`'s own docstring advertises as "the M1 rule (L1.14) one
step on" — cannot fire, because the recorded output resolves perfectly. **Nothing was tampered
with.** No file was edited, no trace was rewritten, no frozen byte was touched; the only act was
a caller using `register_predicate`, which is public API and the documented way to do this.

**This is a regression against M1, not a gap M1 also had.** M1's `@transform` decorator hashes
the function's **source text** into `code_hash` (`transform.py:10`; `:14` says why — *"Hashing
the source means a comment change mints a new descriptor — deliberately (D0084)"*) and refuses a
lambda outright (`transform.py:64-65`: *"a lambda has no name to derive a label from"*). Measured,
with
only a **comment** changed inside the body for M1 and the predicate's **entire behaviour**
changed for M3:

```
                    variant a                          variant b
M1  descriptor_of   sha256:9008e68dc245781f…           sha256:70511b7afe13a37b…   <- moved
M3  node.descriptor sha256:151f4c37062e0e0d…           sha256:151f4c37062e0e0d…   <- identical
```

M1 mints a new descriptor for a comment. M3 does not mint one for a different function.

**How the reasoning inverted.** D0167's own words are that code is referenced by name "because a
lambda has no content address". That is true, and in M1 it is the premise of a *refusal* — a
lambda may not enter a graph. M3 used it as a licence instead, and the shipped catalogue is four
lambdas (`incremental.py:146-151`). The frozen spec says `TraceStore`, `AlwaysRebuild` and
`VerifyingTrace` are "reused **as is**" (m3 §7), and they are — but they are being fed an
identity that no longer carries what M1's carried.

**The in-process guard does not help.** `_register` refuses re-registering a name with a
different object (`incremental.py:98-103`), which is a *process-local* check on a *durable*
artifact: a trace is only useful across runs, and across runs the registry is rebuilt from
empty. Measured: re-registration is refused, and `PREDICATES` is a plain mutable dict exported
in `__all__`, so even the in-process refusal is one assignment away.

**Frozen prose this falsifies.**

- `docs/specs/m3.md:337-338` — *"One derivation, one output, holds because a step is a pure function
  of those inputs"*. A step is not a pure function of `(descriptor, state, ledger, deltas)`; it
  is also a function of the registry, which is in none of them.
- `tests/laws/m3/test_l3_executor.py:79` (frozen L3.15's docstring) — *"A step is a pure
  function of (descriptor, state, ledger, deltas)"*. The test verifies it by replaying the same
  predicate in the same process, which cannot observe the gap.

**Remedy — a decision record, a superseding law, and one code change.** The registries already
hold everything needed: `register_predicate` receives a real function, and `transform._source_text`
already exists and already does the job (dedent, LF-normalise, hash). Registering should mint a
`code_hash` the way `@transform` does and put it in the declared form beside the name, so
`{"predicate_id": "risk-ok", "predicate_code": "sha256:…"}`. That refuses a lambda for the same
reason M1 refuses one, which means the shipped catalogue must be four named functions rather
than four lambdas — a small, mechanical change to unfrozen code. Every existing `deltaop/1`
address moves, which is the freshness mechanism working, not a cost to avoid.

Rejected: hashing `repr(fn)` (addresses, not content); keeping the name and documenting the
caveat (the shortest spelling would still violate the discipline — BRIEF §5).

**Freeze/custody:** `src/tannen/incremental.py` and `src/tannen/transform.py` are unfrozen and
uncustodied, so the code half is builder-landable. The two frozen sentences are not.

## RT-M3-04 — The oracle-shadow guard authenticates a module by what it says about itself, so the M3 kill criterion goes vacuous with the whole gate green. **Critical.**

**This is RT-M2-01 re-opened, against the closure D0142 installed for it.** That closure was
correct about the half it addressed — the *set* of oracle names is now derived off the
filesystem and can no longer lag a milestone. What it did not change is *how* a name is checked:

```python
actual_file = getattr(module, "__file__", None)
actual = Path(actual_file).resolve() if actual_file else None
if actual == frozen[0]:
    continue                                                            # plugin.py:96-99
```

`__file__` is a plain attribute. A decoy that sets it to the frozen path **is** the frozen
module as far as this check is concerned.

**Positive control first, so the guard's input set is known to be non-empty.** A naive decoy —
honest about where it lives — trips the guard exactly as designed:

```
! _pytest.outcomes.Exit: tannen evidence: sys.modules['_delta_model'] is …/tests/conftest.py,
  not the frozen …/tests/laws/m3/_delta_model.py — a differential oracle was shadowed by a
  different module of the same name (RT-M1-01 …; RT-M2-01 …) !
```

**The exploit.** The same decoy plus one line, `__file__ = str(frozen)`, with
`check_differential` — frozen L3.12's entire body, and BRIEF §6's differential kill criterion —
replaced by a stub that returns `None`. Instrumented to count its own calls:

```
$ pytest tests/laws/m3                       # evidence ON

tannen evidence: 16 record(s) written to evidence

$ wc -l < /tmp/p4_decoy_calls.txt
1400                                          # "check_differential called on the DECOY stub"

$ python -I -P scripts/check_manifest.py
check_manifest: OK — frozen paths intact; seals unbroken; custody set current; required
signatures present; tier-c.yaml consistent with the guards
```

Then the whole law suite, all four milestones, with the decoy still in place:

```
$ pytest tests/laws
544 passed, 1 xfailed in 648.74s (0:10:48)
tannen evidence: 52 record(s) written to evidence

$ tannen laws report
L3.12   ok      pass     hypothesis-derandomize   2026-09-05T09:35:27…  sha256:94c965b3c7575288…
…
OK — 52 law(s) carry fresh passing evidence.
```

Zero stale rows, zero missing. **That last line is the completion criterion CLAUDE.md names for
an implementation session, and the one D0170 quotes to say M3 is done.** It says exactly the
same thing while BRIEF §6's kill criterion is `lambda *a, **k: None`.

**The kill criterion was answered 1,400 times by that stub, and L3.12 reports `ok pass` with a
fresh descriptor.** The seals are intact because nothing sealed was touched:
`tests/` is not a sealed directory (`governance/tier-c.yaml` seals `tests/laws`, `tests/poison`,
`governance/schemas`), so a new `tests/conftest.py` needs no manifest row.

**Adding `tests/conftest.py` does move `harness_subject`** — it is inside `_conftests`
(`harness.py:39-43`) — so the M0–M2 evidence goes stale at the moment the decoy lands. That is
not a mitigation, and the 544-test run above is the measurement of why: the report's freshness
test is against the *current* subject, and one run under the decoy rewrites all 52 records for
the current subject. The staleness is real for about ten minutes and then self-heals in the
attacker's favour.

**What makes this worse than a re-run of RT-M2-01, and it is the reason for the severity.**
`tests/poison/oracle-shadow-model/` was installed at the M2 sitting and D0154 item 1 will wire
it into `scripts/custodian.sh` at this one. Verified 2026-09-05: that fixture **does** bite the
shipped guard. So the custody floor is about to start certifying this guard as live — against
the naive variant only. BRIEF §9.1's rule is that a guard which passes its poison is weakened;
the sharper case, and the one the corpus is walking into, is **a guard whose poison tests only
the half it already catches**.

**Remedy — drafted, measured, and staged.**
`docs/redteam/fixture-candidates/oracle-shadow-spoofed/` carries the fixture and
`rt-m3-04-plugin-code-identity.patch`: compare the **code the module answers with** against a
fresh load of the frozen file, function by function, instead of asking it where it came from.
Three spellings were tried and the first two were falsified by measurement; a third defect was
then found in the surviving patch by attacking it (a decoy controls its own `__all__`, so the
export list must be read off the reference, never off the module under test). The directory's
README records all three. Verified both
directions: fires on the spoof naming exactly `['check_differential']`, clean tree green, and
both existing oracle fixtures still bite.

**This does not close the hazard, and that recommendation is now three boundaries old.**
RT-M1-01 said the real fix is a package-qualified import in the frozen law file; RT-M2-01
repeated it; this pass repeats it again. It needs the owner's key because the law files are
frozen. Everything else is defence in depth.

**Freeze/custody:** `src/tannen/laws/plugin.py` is neither manifested nor custody-set, so the
patch is builder-landable; installing anything under `tests/poison/` is the Tier-C
`trust-root-changes` door and is owner work.

## RT-M3-02 — The contagion rule's operator set is a hand-maintained enumeration whose one silently-failing member is covered by no frozen law. **High.**

```python
_ALWAYS_REPLAYS = frozenset({"distinct", "aggregate", "anti_join"})     # incremental.py:260
...
self.replay = replay or operator in _ALWAYS_REPLAYS                     # incremental.py:292
```

Grepped repo-wide: `_ALWAYS_REPLAYS` appears in exactly two places, both inside
`incremental.py`. Nothing derives it, and nothing asserts it. Its siblings `_REQUIRED` and
`_ARITY` are the same shape — three hand-written operator enumerations, shipped in the milestone
whose sitting is closing that defect class as a standing rule (D0171 ruling 3, D0172).

**The set is correct today. That is not the finding.** The finding is what happens if it is
ever wrong, and the answer differs per member. Measured by emptying the set and comparing each
operator's delta-maintained stream against the one-shot answer over the same net data:

```
  select       delta-maintained == one-shot ? True
  project      delta-maintained == one-shot ? True
  map_rows     delta-maintained == one-shot ? True
  union        delta-maintained == one-shot ? True
  join         delta-maintained == one-shot ? True
  distinct     RAISED SemiringError: Z: -1 has no set image (docs/specs/m1.md §2.1)
  aggregate    RAISED SemiringError: Z: -1 has no bag image — a negative multiplicity is the delta…
  anti_join    delta-maintained == one-shot ? False
```

**Two of the three members are independently protected and one is not.** `distinct` and
`aggregate` hit the M1 cone raises that D0158 re-commissioned as the executor's tripwire — drop
them from the set and you get a loud refusal. `anti_join` hits nothing. Its payload:

```
  SHIPPED (anti_join in set)   node.replay = True
    maintained integral      [(('k', 2), ('x', 7))]
    one-shot reference       [(('k', 2), ('x', 7))]
    byte-identical?        True

  MUTANT  (anti_join out)      node.replay = False
    maintained integral      [(('k', 1), ('x', 5)), (('k', 2), ('x', 7))]
    one-shot reference       [(('k', 2), ('x', 7))]
    byte-identical?        False
```

`k=1` should have been anti-joined away when B gained it. It survives — the stale-retention
unsoundness D0163 documented, silently.

**The frozen law suite does not cover it.** With `anti_join` removed from `_ALWAYS_REPLAYS`:

```
$ pytest tests/laws/m3
38 passed in 27.90s

$ pytest tests/test_incremental.py
2 failed, 26 passed
FAILED tests/test_incremental.py::test_the_contagion_rule_sheds_a_superseded_anti_join_address
FAILED tests/test_incremental.py::test_a_column_parameters_order_is_not_part_of_the_declared_node
```

The rule **is** caught — by `tests/test_incremental.py`, which is not under `tests/laws/` and is
therefore **not sealed**: an ordinary file any builder may edit. The second failure is
incidental (a descriptor-equality assertion). So the shipped embodiment of §4's contagion rule
is pinned by one unsealed test and by no frozen law.

**Why the frozen laws miss it, stated by the frozen files themselves.** L3.11/L3.12 kill the
`antijoin-delta-maintained` mutant — the repo already knows this failure mode by name — but they
decide replay by re-implementing the rule inside the subject adapter:

```python
# -- the contagion rule (§4, §7). The adapter is `run_ticks`'s caller-side policy,
# and the rule is the spec's: a node replays iff an anti_join lies at or below it.
# The shipped executor's own embodiment of the rule is L3.15's business.
def replays(self, plan): ...                      # _delta_subject.py:149-158, walks the plan tree
```

The deferral is to L3.15 — and every `DeltaNode` in `test_l3_executor.py` is `select` or
`project`, unary, never an `anti_join` (an `anti_join` has arity 2). The graph law defers to the
executor law, and the executor law never exercises a binary node. So the mutant dies against the
*model*, and the identical defect in the *shipped package* passes every frozen law.

**Remedy.** The empirical derivation above is the guard: run each operator's stream both ways
and assert that the set of divergent-or-raising operators equals `_ALWAYS_REPLAYS`. That is
ruling (3)'s "derive AND assert" shape exactly, it costs one test in the unsealed
`tests/test_incremental.py`, and it needs no key. A poison fixture is the wrong instrument here
— there is no guard yet to poison; the fixture belongs with the guard, at the sitting after the
one that installs it. Worth recording alongside: the three-member set has unequal failure modes,
and only `anti_join`'s is silent.

**Freeze/custody:** `src/tannen/incremental.py` and `tests/test_incremental.py` are both
unfrozen and uncustodied.

## RT-M3-03 — `anti_join`'s two operand orders share one `step_id`, and the premise of the still-unsigned D0171 ruling (2) is false. **High.**

`derivation_id` is order-insensitive over its inputs — frozen M1 semantics (m1 §8, L1.13), and
`advance` inherits it deliberately (`incremental.py:401-407`, D0167). The conferral raised it,
and D0171 ruling (2) kept it:

> `derivation_id` STAYS ORDER-INSENSITIVE; NO WIDENING AT M4. … Changing it invalidates evidence
> across three milestones to fix a case where a caller passes operands in the wrong order — **a
> caller error the type system should catch**, not the identity scheme.

The premise is testable, so it was tested. `anti_join(A, B)` and `anti_join(B, A)` are different
questions; give both relations the **same schema** and there is nothing for a type system to
catch:

```
one-shot reference:
   anti_join(A, B) = [(('k', 2), ('v', 20))]
   anti_join(B, A) = []

advance(node, [A, B])  step_id = sha256:7e1fc9687080dbd8590c87ad345b6bc4f1e81598da1e91433097281c2f6f6a21
                       rebuilt = True
                       result  = [(('k', 2), ('v', 20))]

advance(node, [B, A])  step_id = sha256:7e1fc9687080dbd8590c87ad345b6bc4f1e81598da1e91433097281c2f6f6a21
                       rebuilt = False
                       result  = [(('k', 2), ('v', 20))]      <- should be []

same step_id for opposite operand orders? True
was the swap refused by anything?         no exception was raised
```

Control, with a fresh trace store: `[B, A]` returns `[]`, correctly, `rebuilt=True`. **The trace
is what corrupts it**, exactly as in RT-M3-01, and again with `rebuilt=False` reporting the
wrong answer as a cache hit.

**D0171 is `status: blocked-on-owner` and explicitly unsigned**, so this is reaching the sitting
before the ruling is enacted rather than after — which is the useful time for it. The ruling's
*conclusion* may well still be right: widening `derivation_id` does invalidate evidence across
three milestones, and that is a real price. What is not right is the stated reason. Nothing in
the type system distinguishes `anti_join(A, B)` from `anti_join(B, A)` when the schemas agree,
and the executor does not merely fail to catch the swap — it answers it from the trace.

**Remedy, and it is cheap and local.** Do not touch `derivation_id`. The asymmetry belongs to
the operator, not to the identity scheme, so it can be carried in the part of the step identity
the node already controls. Two spellings, either of which works: give the *step's* inputs a role
rather than a position — fold `{"left": ref_a, "right": ref_b}` into the derivation for a
non-commutative operator, so the two orders are two derivations because they are two different
input values — or have `advance` refuse a bare positional pair for such an operator and require
named operands, which turns the swap into an error at the call rather than an answer from the
trace. Either keeps m1 §8 and L1.13 untouched and leaves every existing `deltaop/1` descriptor
valid.

Also worth putting to the sitting: `union` and `join` are genuinely commutative here, so
order-insensitivity is *correct* for them and the blanket rule is only wrong for `anti_join`.
The set of non-commutative binary operators is, today, exactly `{anti_join}` — and per ruling
(3) it should be derived, not written down, or it becomes the ninth instance of D0172's class.

**Frozen prose this touches.** `docs/specs/m3.md:336-337` — *"Every step is its own derivation:
the existing `derivation_id` over the step's descriptor and its content-addressed inputs —
`(state_ref, ledger_ref, sorted delta refs)`"*. The word `sorted` is the defect, in frozen text.
D0167 records the inheritance as deliberate, so this is a known choice whose consequence was not
measured, not an oversight.

## RT-M3-05 — M3 is the first milestone with fewer law nodes than laws; five nodes carry twelve of sixteen. **Medium.**

D0169 fixed a real defect: `LAW_TEST_RE` read only the leading law number, so seven frozen M3
laws were invisible to discovery, to the report and to the evidence stream, and §11's own
completion criterion was unmeetable. The fix reads the range. What the fix also does is make a
single passing node write **four** evidence records.

Measured across every milestone:

```
m0: 10 laws,  25 law nodes; nodes claiming >1 law: 0 covering  0 laws
m1: 17 laws, 117 law nodes; nodes claiming >1 law: 0 covering  0 laws
m2:  9 laws,  29 law nodes; nodes claiming >1 law: 0 covering  0 laws
m3: 16 laws,  12 law nodes; nodes claiming >1 law: 5 covering 12 laws
    test_l3_1_through_4_the_delta_calculus                          -> L3.1, L3.2, L3.3, L3.4
    test_l3_7_and_8_integrated_operators_consume_integrals_never_deltas -> L3.7, L3.8
    test_l3_9_and_10_source_convergence                             -> L3.9, L3.10
    test_l3_11_and_12_graph_convergence_and_the_residue_theorem     -> L3.11, L3.12
    test_l3_13_and_14_the_multi_why_door_and_the_encode_gate        -> L3.13, L3.14
```

M0, M1 and M2 ran at 2.5×, 6.9× and 3.2× nodes per law, and **no** node in any of them claimed
more than one law. M3 runs at 0.75×, and 12 of its 16 laws have no node of their own. The
evidence store cannot tell the difference: `tannen laws report` shows sixteen healthy M3 rows,
and each of the four rows for L3.1–L3.4 carries `examined={"law_nodes": 1, …}` for the same
single node.

**This is not an argument for reverting D0169** — before it, those laws had no evidence at all,
