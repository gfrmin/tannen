## RT-M1-01 — A frozen oracle module can be shadowed by name through `sys.modules`, undetected. **Critical.**

**Claim.** `tests/laws/m1/test_l1_duckdb.py` (frozen, manifested) — the home of L1.16,
BRIEF §6's differential kill criterion — loads its oracle half with a bare
`import _fragment as F`. `tests/` carries no `__init__.py` anywhere in this repo, so
D0089's frozen `tests/laws/m1/_fragment.py` is a plain top-level module, not a package
member, and Python caches imports by NAME in `sys.modules`. Anything that gets a
DIFFERENT module also named `_fragment` into `sys.modules` first wins the race: pytest's
default "prepend" import mode inserts a test file's own directory at `sys.path[0]` when
that file is collected, so a new, unmanifested `tests/conftest.py` (that directory is
**not** sealed — only `tests/laws` and `tests/poison` are) doing `import _fragment` gets
collected before `tests/laws/m1/` and wins.

**Reproduction** (two new, untracked files, neither under a sealed directory, no
manifest row needed for either):

```python
# tests/_fragment.py — a faithful decoy: re-exports the real frozen module so every
# test still behaves identically, plus a marker to prove which module actually ran.
import importlib.util as _ilu
from pathlib import Path as _Path
_REAL = _Path(__file__).resolve().parent / "laws" / "m1" / "_fragment.py"
_spec = _ilu.spec_from_file_location("_fragment_real_redteam", _REAL)
_real = _ilu.module_from_spec(_spec)
_spec.loader.exec_module(_real)
for _name in dir(_real):
    if not _name.startswith("__"):
        globals()[_name] = getattr(_real, _name)
REDTEAM_SHADOW_MARKER = "this is tests/_fragment.py, NOT the frozen tests/laws/m1/_fragment.py"
```

```python
# tests/conftest.py
import sys
import _fragment  # noqa: F401
print(f"\n[REDTEAM] tests/conftest.py primed sys.modules['_fragment'] = {_fragment.__file__}")

def pytest_sessionfinish(session, exitstatus):
    mod = sys.modules.get("_fragment")
    print(f"\n[REDTEAM] sys.modules['_fragment'].__file__ = {getattr(mod, '__file__', None)}")
    print(f"[REDTEAM] marker = {getattr(mod, 'REDTEAM_SHADOW_MARKER', '<not shadowed>')}")
```

```
$ .venv/bin/python -I -P -m pytest tests/laws/m1/test_l1_duckdb.py -q --no-header -s \
    -k test_l1_16_the_catalogue_covers_every_operator_of_the_fragment

[REDTEAM] tests/conftest.py primed sys.modules['_fragment'] = /home/…/tests/_fragment.py
.tannen evidence: 0 record(s) written to evidence; 1 law(s) partly run, no record: L1.16

[REDTEAM] sys.modules['_fragment'].__file__ = /home/…/tests/_fragment.py
[REDTEAM] marker = this is tests/_fragment.py, NOT the frozen tests/laws/m1/_fragment.py

1 passed, 67 deselected in 0.11s
```

`import _fragment as F` inside the frozen `test_l1_duckdb.py` silently bound to the
decoy at `tests/_fragment.py` for the entire session; the test reported **1 passed**;
`scripts/check_manifest.py` reported `OK` (neither new file is under a sealed
directory, so the seal check has nothing to say about them):

```
$ uv run python scripts/check_manifest.py
check_manifest: OK — frozen paths intact; seals unbroken; custody set current;
required signatures present; tier-c.yaml consistent with the guards
```

**Why it matters.** A faithful decoy is undetectable by construction — the point of the
proof-of-concept is the substitution mechanism, not a specific weakened oracle — but the
mechanism generalises directly to a harmful one: an attacker (or an honest mistake — see
below) that overrides `evaluate()`'s dispatch for one operator to bypass the real
`tannen.kernel.ops` call and instead compute an independently-"correct" answer would
decouple L1.16's differential comparison from the code it is supposed to be testing,
for exactly that operator, while `test_l1_16_the_catalogue_covers_every_operator_of_the_fragment`
(which only checks that the plan/catalogue *mentions* every operator name, never that
`evaluate` executes it through the real implementation) keeps reporting full coverage.
This is RT-03 from the M0 report (a conftest that "restores the refusal" so a broken
*implementation* passes a frozen law) with the target moved to the oracle half instead
of the implementation half — the M0 closure (`check-manifest-sealed/`, sealed
directories) does not reach it, because neither new file sits inside a sealed
directory.

**Exploitable by accident?** Partially. A `tests/conftest.py` is a routine thing to add
(there is currently none), and choosing a helper module name that happens to collide
with a frozen law's bare import is the kind of coincidence that goes unnoticed for a
long time in a repo with no package `__init__.py` files anywhere under `tests/`. The
faithful-decoy shape used for proof here is not an accident, but the underlying naming
hazard is live regardless of intent.

**Severity: critical.** It reaches BRIEF §6's stated kill criterion and the one frozen
file whose entire job is to be an independent oracle (D0089: "an oracle Session B can
edit is not an oracle" — this shows an oracle Session B does not even have to edit).

**Closed in this session, partially — defence in depth, not the real fix.**
`src/tannen/laws/plugin.py`'s `LawEvidencePlugin.pytest_collection_modifyitems` now
checks, unconditionally (even under `TANNEN_NO_EVIDENCE`), whether `sys.modules`
holds an `_fragment` module and, if so, whether its `__file__` resolves to the frozen
`tests/laws/m1/_fragment.py`; a mismatch calls `pytest.exit(...)` and aborts the run
naming RT-M1-01. Verified both ways: the reproduction above now aborts with
`! _pytest.outcomes.Exit: tannen evidence: sys.modules['_fragment'] is
/home/…/tests/_fragment.py, not the frozen /home/…/tests/laws/m1/_fragment.py
(RT-M1-01: …)`, and the real tree is unaffected (`_fragment` resolves to the frozen
path when nothing shadows it). A permanent regression test,
`tests/test_laws_runner.py::test_a_shadowed_oracle_module_is_refused`, constructs the
shadow itself (a tmp decoy + a tmp `-p` bootstrap plugin on `PYTHONPATH`, never by
writing into the real `tests/` tree — D0092's rule) and asserts the run is refused.

**This does not close the naming hazard itself** — only detect one exploitation of it,
and only for this one frozen file's one bare import. The real fix is a
package-qualified import in `tests/laws/m1/test_l1_duckdb.py` (e.g.
`from tests.laws.m1 import _fragment as F`, which needs `__init__.py` files under
`tests/`, `tests/laws/`, `tests/laws/m1/`, and possibly a `pyproject.toml`
`[tool.pytest.ini_options]` import-mode change to `importlib`) or an
`importlib.util.spec_from_file_location` load keyed by an unambiguous name. `test_l1_duckdb.py`
is frozen and manifested (`m1-laws-freeze`), so this is exactly CLAUDE.md's
"the frozen laws turn out to be wrong" case: not edited in place, but recorded as a
defect and superseded at the next boundary sitting. **Queued for the owner.**

## RT-M1-02 — The harness subject still misses two classes of input that decide how hard a law was tested. **Medium** (one item), **refuted** on the rest.

RT-09 (M0) widened `implementation_subject` to `harness_subject`: every file under
`src/tannen`, root `conftest.py`, `pyproject.toml`, every `tests/**/conftest.py`. This
probe re-checked the specific list of candidates named in the M1 task brief.

**Refuted:**

- `pytest.ini` / `tox.ini` / `setup.cfg` do not exist in this repo (`pyproject.toml`'s
  `[tool.pytest.ini_options]` is the only config, and it is already in `HARNESS_FILES`).
  Nothing to widen.
- `uv.lock` sits outside `harness_subject` and outside `MANIFEST.sha256`, but every
  dev dependency that matters to a law run — `hypothesis`, `pytest`, `jsonschema` — is
  pinned **exactly** (`==`) in `pyproject.toml` itself, which **is** hashed. Editing
  `uv.lock` alone without moving `pyproject.toml`'s exact pins does not change what

- `.hypothesis/` (the on-disk example database): `settings.register_profile` in the
  root `conftest.py` sets `derandomize=True`, and Hypothesis's own settings code raises
  if you pass both `derandomize=True` and a non-default `database`, and documents that

  `.venv/lib/python3.13/site-packages/hypothesis/_settings.py` directly (line ~687,
  ~1228). The tannen-laws profile never reads or writes `.hypothesis/`. Not exploitable

**Confirmed — `.venv/` site-packages contents (and, by the same argument, any `.pth`

An installed package's actual source — the code that runs `@given` strategies, does
the shrinking, or (for `duckdb`) executes the SQL the L1.16 differential law compares

be written to routinely (`uv sync`), so there is no natural place to hang a hash check
without also re-deriving the whole environment on every guard run.

**Exploitable by accident?** Low — this requires deliberately editing installed
package source, which `uv sync --frozen` would normally overwrite on the next sync.
It is closer to a supply-chain question (is the .venv's content attested anywhere)
than a builder-mistake one.

**Closure:** not attempted in this session — no file in the editable set
(`harness.py`, `plugin.py`, `report.py`) can reach into `.venv/` without either hashing
a large, frequently-changing, gitignored tree (expensive, and itself only as trustworthy
as the guard's own interpreter, which lives in that same tree) or pinning package
hashes via `uv.lock` and verifying them against installed `.dist-info/RECORD` at guard
time — a real mechanism, but a bigger one than this session should reach for without an
owner decision on the cost. **Queued.**

## RT-M1-04 — A hand-rewritten trace file is served as a legitimate cache hit for the wrong derivation. **Confirmed** (Task 8's hypothesis). **Medium-high.**

**Claim** (this session's Task 8 flagged it as unverified going in): `TraceStore`'s
write-once guarantee is enforced only through its own `record()` method
(`existing = self.lookup(derivation); if existing not in (None, output_ref): raise
TraceIntegrityError`). The trace directory is a plain directory of plain files —
`derivation_id -> output_ref`, one file per derivation — with no permissions or
integrity binding of its own. `VerifyingTrace.build` on a hit calls
`store.get_bytes(recorded)`, which verifies that `recorded` **resolves to some valid
content in the store** (content-hash-addressed, so *that* check is real), but never
checks that the resolved content is actually the derivation's own correct output.

**Reproduction:**

```python
node_a = Node(keep_positive, (ref,))   # rows where k > 0
node_b = Node(keep_negative, (ref,))   # rows where k < 0 -- a DIFFERENT derivation
built_a = AlwaysRebuild().build(node_a, store, traces)
built_b = AlwaysRebuild().build(node_b, store, traces)
# both outputs are distinct, valid, resolving store objects

trace_path = traces._path(node_b.derivation_id)
trace_path.write_text(built_a.output_ref + "\n")   # hand-rewrite B's trace to A's ref
                                                     # -- NOT via TraceStore.record()

result = VerifyingTrace().build(node_b, store, traces)
```

```
A derivation_id: sha256:47328f94… -> output sha256:e6c96996…
B derivation_id: sha256:5d55cb59… -> output sha256:1d62f172…
B trace file rewritten to A's ref by hand (NOT via TraceStore.record()).
VerifyingTrace().build(node_b, ...) -> Built(derivation_id='sha256:5d55cb59…',
  output_ref='sha256:e6c96996…', rebuilt=False, layer=None, operators=frozenset())
CONFIRMED: VerifyingTrace served node A's output as a legitimate hit for node B's
derivation, with rebuilt=False and no error.
```

**Why this is not simply "the frozen law is wrong."** `docs/specs/m1.md` §8 describes
exactly this behaviour: *"[VerifyingTrace] verifies that the recorded output resolves
in the store and that the store's verify-on-read passes, and raises
`TraceIntegrityError` if it does not."* It never claims to check that the resolved
object is *correct* for the derivation, only that *something valid* resolves. The
frozen law `tests/laws/m1/test_l1_executor.py::test_l1_14_a_tampered_stored_output_is_detected`
tests a different, narrower thing — corrupting the STORE object's bytes in place
(caught by the store's own content-hash verify-on-read) — never a trace file rewritten
to point at a different, still-valid object. Neither the spec text nor the frozen law
promises what this probe breaks, so this is a genuine trust-boundary gap rather than
a law violation, and `make verify` has nothing that could have caught it.

**Severity: medium-high.** It means the append-only store's marketing claim — "a
recorded output that has gone missing or been altered is not a cache miss… the store's
append-only and write-once, so its absence means something happened outside the
store's contract" — does not extend to "a recorded output was swapped for a different,
equally valid one." Any process (or bug) with filesystem access to a `TraceStore`
root, without needing store write access at all, can silently redirect any derivation
to serve any other derivation's output.

**Exploitable by accident?** Low on its own (needs direct trace-file editing), but the
*shape* of the gap — the trace directory has no protection beyond the API surface that
happens to be the only thing calling it today — is exactly RT-03/RT-M1-01's family:
a guarantee that holds only because nothing has needed to route around it yet.

**Closure:** not attempted in this session. `src/tannen/executor.py` is not frozen and
was not in the pre-approved editable set for this pass, and more to the point: a real
fix is a design decision, not a bug fix. Recomputing on every `VerifyingTrace` hit
defeats the entire purpose of a trace (and arguably breaks L1.14's intent, which
explicitly distinguishes a verified hit from a rebuild). Binding trace entries to their
derivation cryptographically or structurally (e.g. storing `H(derivation_id,
output_ref)` instead of a bare ref, or embedding the derivation id in the stored
content itself) is exactly the kind of "wire schema" question D0088 deferred the
Governor's Request/Response shape over — this could reasonably be folded into that
M4 discussion rather than bolted on ad hoc now. A cheaper, purely defensive option
(marking trace files read-only after `record()` writes them) was considered and
rejected here: on a single-user filesystem with no privilege boundary between the
process that writes traces and any process that could tamper with them, `chmod`
raises the cost of an accidental overwrite to near zero real security value against a
deliberate one — worth doing eventually, not worth pretending it closes this.
**Queued for the owner / an M2–M4 discussion.**

## RT-M1-05 — A single skipped test inside a whole-FILE pytest binding reads as fully enforced. **High.** **Fix drafted and verified; not landed — see addendum.**

**Claim** (this session's Task-brief hypothesis, confirmed): `check_decisions.py`'s
`pytest_violation` treated a run as "skipped" (a binding failure) only when **nothing
in it passed**: `re.search(r"\b[1-9]\d* skipped\b", out) and " passed" not in out`. The
majority of this repo's pytest bindings target a whole FILE, not one node — a quick
survey of `decisions/*.yaml` turns up 20+ file-level pytest bindings, including
`tests/laws/m1/test_l1_executor.py` (D0083, D0100), `tests/laws/m1/test_l1_duckdb.py`
(D0089, D0098, D0101), `tests/laws/m1/test_l1_replay.py` (D0100, D0101),
`tests/laws/m0/test_l0_encoding.py` (D0006), and `tests/test_governance_scripts.py`
(D0063) itself. If one test function in a bound file is skipped — a `pytest.mark.skip`,
a runtime `pytest.skip()`, an `importorskip` that starts failing — while its siblings in
the same file keep passing, the run exits 0, and the guard has never distinguished that
from full enforcement.

**Reproduction** (self-contained tree, no real repo file touched):

```yaml
# decisions/0001-poison-file-skip.yaml
id: D0001
tier: A
status: accepted
bindings:
  - type: pytest
    target: tests/test_mixed.py
```
```python
# tests/test_mixed.py
def test_this_one_passes():
    assert True

@pytest.mark.skip(reason="the enforcement this binding claims never actually runs")
def test_this_one_is_skipped():
    assert False
```

```
$ uv run python scripts/check_decisions.py --root <tree>
check_decisions: OK — 1 records valid; 1 pytest binding(s) green; 0 unenforced …
```
Fully green, `EXIT=0`, despite the binding's one substantive test never running.

**Why this is not hypothetical against the real repo**: it is live today against
every file-level binding named above. Nothing in this repo currently has an
unexplained skip, but nothing was stopping one from landing silently either — the
guard would report the same "N pytest binding(s) green" line either way.

**Severity: high.** Bindings are the mechanism CLAUDE.md and BRIEF §9 both describe as
what makes a decision "load-bearing"; a whole-file binding is the common case, not an
edge case, and this made the common case unable to see a partial regression inside
itself.

**Drafted and verified this session; not landed as a commit (see addendum below).**
`scripts/check_decisions.py` (`pytest_violation`) now runs
`pytest -rs` (which prints `SKIPPED [n] file:line: reason` per skip) and flags **any**
skip whose reason does not start with an explicit allow-listed prefix
(`ALLOWED_SKIP_REASON_PREFIXES = ("S-pending: ",)`) even when other tests in the same
run passed. The allow-list is not a loophole opened for this fix: it documents the one
skip this repo already has on purpose — `tests/test_conformance.py`'s
`pytest.skip(f"S-pending: {...}")` for a concept grade with no published vectors yet
(D0009), bound at file granularity by D0087 — which is DESIGNED to skip and must not
regress into a guard failure. Verified both ways: the poison tree above now fails with
`pytest node has an unexplained skip … (RT-M1-05: …)`, and the real repo's own
`tests/test_conformance.py` binding (17 passed, 1 allow-listed skip) stays green. A
permanent regression test,
`tests/test_governance_scripts.py::test_a_skip_hidden_inside_a_passing_file_binding_is_caught`,
constructs the exact scenario above inside a `tmp_path` tree (D0092's rule) and pins
the fix; it also explicitly clears `TANNEN_CHECK_DECISIONS_NESTED` from its own
subprocess call (RT-08's hatch), since this test itself may run nested inside another
`check_decisions.py` invocation resolving D0063's file-level binding to this very
file — that composition was caught live while building this fix (the naive version of
this test failed exactly when run that way and passed standalone, which would have
been an M1 analogue of D0091/D0092's "borrowed its precondition from mutable
context" defect had it shipped).

**Addendum (found while attempting to commit this fix, after the rest of this pass was
otherwise complete): the expected custody drift cascades into the pre-commit gate
itself, so the fix could not be landed as an ordinary builder commit.**
`scripts/check_decisions.py` is a member of the custody set (`governance/tier-c.yaml`'s
`custody.set` — the positive enumeration the owner's key vouches for, D0061), so editing
it necessarily makes `governance/custody.sha256` stop matching its bytes.
`scripts/check_manifest.py` and `scripts/custodian.sh` both correctly report this as
custody drift — that is the custody floor doing its job, and RT-04's own M0 closure text
already says so verbatim ("this is the alarm, not a bug"). What was not anticipated
when the "Closed in this session" line above was first written: D0063 (Tier C, ruling 3)
binds `tests/test_governance_scripts.py` at file granularity, and that file contains
`test_check_passes_on_real_tree[check_manifest.py]`, which runs `check_manifest.py`
against the real tree and asserts it exits 0. The moment `scripts/check_decisions.py`'s
bytes differ from `governance/custody.sha256`, that one test goes red — permanently,
until the owner re-signs — which makes D0063's own binding unresolved, which is exactly
what `.pre-commit-config.yaml`'s `check-decisions` hook checks on every commit. Reproduced
directly: with the fix applied to the working tree (uncommitted), `env -u
TANNEN_CHECK_DECISIONS_NESTED .venv/bin/python scripts/check_decisions.py` against the
real repo root reports `decisions/0063-conferral-rulings.yaml: binding does not resolve
— pytest node fails: tests/test_governance_scripts.py`, and `git commit` is refused by
the `check-decisions` pre-commit hook for the same reason — not a transient failure, a
structural one that persists across every subsequent commit attempt for as long as the
fix sits in the tree.
