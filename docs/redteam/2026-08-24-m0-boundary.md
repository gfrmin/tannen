## RT-01 — Deleting a row from `MANIFEST.sha256` unfreezes the path, silently. **Critical.**

**Claim.** The manifest is a whitelist of hashes that does not list itself, and nothing
enumerates what it ought to contain. Removing a row unfreezes that path with no guard
reaction at all.

**Reproduction** (throwaway worktree at `8ad2087`):

```sh
sed -i '/tests\/laws\/m0\/test_l0_store.py/d' MANIFEST.sha256   # one line, one file
# gut the frozen law L0.6 so it asserts nothing:
#   test_l0_6_gc_refuses now reads `store.gc()` with the four assertions deleted
# and make the implementation violate it — Store.gc() now unlinks every object:
#   for path in sorted(self._objects.rglob("*")): path.unlink()
rm -rf evidence && make verify
```

Observed, complete and green:

```
check_manifest: OK — frozen paths intact; tier-c.yaml consistent with the guards
check_concepts: OK — 8 records, artifacts complete, CONCEPTS.md fresh
check_decisions: OK — 47 records valid; 15 pytest binding(s) green; ...
142 passed, 1 skipped in 13.42s
L0.6    ok      pass     -    2026-08-24T14:33:04.293534+00:00  sha256:718b0c1e7cb48f14…
OK — 10 law(s) carry fresh passing evidence.
Contracts: 3 kept, 0 broken.
custodian: frozen-path hashes verify
custodian: custody set and CI config are manifested
custodian: guard 'check_manifest' fails its poison as required
custodian: custody floor intact
```

So: `Store.gc()` deletes every object in the store — BRIEF §10 "No store mutation,
ever", `governance/tier-c.yaml` `guard_enforced: store-mutation`, the law L0.6 that
exists to prevent exactly this — and the whole gate is green.

**How much of the manifest is exposed.** 27 rows. `scripts/custodian.sh` check 2
hard-codes 11 of them (`custodian.sh`, `allowed_signers`, `ci.yml`, and everything under
`tests/poison/`). Another 9 are protected only *incidentally*, by a `type: manifest`
binding in some decision record — which is itself an editable YAML file (see RT-12).
That leaves **7 rows removable with no trace whatsoever**, enumerated live:

```
tests/laws/m0/test_l0_descriptor.py
tests/laws/m0/test_l0_store.py
tests/laws/evidence-vectors/negative/bad-law-id.json
tests/laws/evidence-vectors/negative/malformed-descriptor-ref.json
tests/laws/evidence-vectors/negative/missing-verdict.json
tests/laws/evidence-vectors/positive/minimal-pass.json
tests/laws/evidence-vectors/positive/property-fail-with-descriptor.json
```

Two of the seven are frozen M0 law files. (The `BRIEF.md` row *is* protected — D0022
happens to carry `type: manifest, target: BRIEF.md`. Removing that row is caught by
`check_decisions`, which I confirmed. That is luck, not design.)

**Severity: critical.** It reaches BRIEF §10 non-goals, the frozen law suite and the
Tier-C door `trust-root-changes` in one `sed`.

**Exploitable by accident?** No — deliberate cheating only. But note the failure is
*silent* in the other direction too: an owner regenerating the manifest with an
incomplete `find` would drop rows and never be told.

**Closure:** `check-manifest-sealed/` (sealed directories) + a `MANIFEST.sha256.sig`
required to exist (see RT-04's patch, whose `OWNER_SIGNED` list already includes it).

## RT-02 — The import contracts are configuration, and nothing checks the configuration. **Critical.**

**Claim.** The seeded lead is half right and half wrong. The real contracts *do* bite
an unmodified tree. What nothing checks is whether they are still the contracts
`governance/tier-c.yaml` describes — and three independent edits neuter them while
every guard stays green.

**Control first** (so the lead is settled): plant `import os` / `import datetime` in
`src/tannen/kernel/refs.py`, run `uv run lint-imports`:

```
Contracts: 1 kept, 2 broken.
tannen.kernel is not allowed to import os:  -   tannen.kernel.refs -> os (l.13)
```

The contracts are live. Now the three neuterings, each with the forbidden import left
in place:

**(a) `ignore_imports`.** Add to both kernel contracts in `pyproject.toml`:

```toml
ignore_imports = ["tannen.kernel.** -> **"]
```

`uv run lint-imports` → `Contracts: 3 kept, 0 broken`. Full `make verify` → green
end to end, custodian included, while `tannen.kernel.refs` imports `os` and `datetime`.

**(b) Narrowed `source_modules`.** `["tannen.kernel"]` → `["tannen.kernel.refs"]`, with
`import subprocess` / `import random` planted in `src/tannen/kernel/encoding.py`
(nothing under `tannen.kernel.refs` imports it, so the narrowed source never sees it):

```
Contracts: 3 kept, 0 broken.
check_manifest: OK — frozen paths intact; tier-c.yaml consistent with the guards
```

**(c) Delete the module from both sources of truth.** `governance/tier-c.yaml` is
**not in `MANIFEST.sha256`** (0 rows match it — see RT-13). Remove `os`, `subprocess`,
`datetime` from its `forbidden_imports` *and* from the `pyproject.toml` contracts, and
`check_manifest`'s D0016 consistency check is satisfied because it only checks
tier-c → pyproject coverage, never the reverse and never the contract's shape:

```
13:import os          # RED TEAM
14:import subprocess  # RED TEAM
15:import datetime    # RED TEAM
kernel imports no IO modules (BRIEF §5.3) KEPT
check_manifest: OK — frozen paths intact; tier-c.yaml consistent with the guards
custodian: custody floor intact
```

In the same edit I deleted the whole `trust-root-changes` Tier-C door from
`tier-c.yaml`. No guard noticed.

**Why the poison corpus misses all three.** `tests/poison/lint-imports/` builds a
synthetic `poisonpkg` and checks it against a synthetic contract in its own
`pyproject.toml`. It proves import-linter is installed and runs. It contains no
reference to `tannen`, `kernel-no-io`, `kernel-no-clock` or `no-cross-repo`. Under all
three neuterings above it still exits non-zero with `BROKEN`, so the custodian reports
`guard 'lint-imports' fails its poison as required`.

**Severity: critical.** `kernel-io` and `kernel-clock` are `guard_enforced`
impossibilities in `tier-c.yaml` — the whole argument for them not needing owner
approval is that the guard makes them impossible.

**Exploitable by accident?** Spelling (b) yes — narrowing a contract to "the module I
am working on" is a plausible good-faith debugging edit that is easy to leave behind.
(a) and (c) are deliberate.

**Closure:** `lint-imports-kernel/` fixture (covers (a) and (c); **verified both
ways** — it bites today and goes silent exactly when the contracts are neutered) plus
the contract-shape check drafted in `check-manifest-sealed/`'s patch (covers (b)), plus
a manifest row for `governance/tier-c.yaml`.

## RT-03 — Frozen directories are whitelists, not seals: a new file changes what the frozen laws mean. **Critical.**

**Claim.** `MANIFEST.sha256` pins the bytes of files it lists. It says nothing about
files it does not list, including new ones placed *inside* a frozen directory. A
`conftest.py` added to `tests/laws/m0/` can rewrite the implementation under the frozen
laws, and it is invisible to every guard and to the law descriptors.

**Reproduction.** Same violating `Store.gc()` as RT-01 (deletes every object), manifest
untouched, law file untouched, and one new file:

```python
# tests/laws/m0/conftest.py
import pytest

@pytest.fixture(autouse=True)
def _restore_the_refusal(monkeypatch):
    from tannen.store import GC_REFUSAL, Store
    def gc(self):
        print(GC_REFUSAL)
        return GC_REFUSAL
    monkeypatch.setattr(Store, "gc", gc)
```

`make verify`:

```
142 passed, 1 skipped in 21.33s
L0.6    ok      pass     -   2026-08-24T14:27:26.719720+00:00  sha256:40c232f41f43e610…
OK — 10 law(s) carry fresh passing evidence.
custodian: custody floor intact
```

L0.6 is reported as carrying fresh passing evidence for the current descriptors while
the implementation it is evidence about deletes store objects.

**Confirmed separately:** adding `tests/laws/m0/conftest.py` leaves **every** M0
descriptor unchanged (see RT-09), so the evidence stream cannot see it either.

**Severity: critical.** This is the cleanest possible defeat of the freeze: nothing
frozen was touched.

**Exploitable by accident?** Genuinely yes. Adding a `conftest.py` to a test directory
is routine. An autouse fixture that patches a module for convenience, left in place, is
an ordinary mistake with this exact consequence.

**Closure:** `check-manifest-sealed/` — every file under a sealed directory must carry
a manifest row. One check closes RT-01 and RT-03 together.

## RT-04 — Deleting `governance/policy.yaml.sig` silently lowers the custody floor. **High.**

**Claim.** `scripts/custodian.sh` check 4 verifies the policy signature *only if the
signature file exists*: `if [ -f governance/policy.yaml.sig ]`. Deleting the signature
returns the repo to its pre-opening state, the custodian says so reassuringly, and
exits 0. Neither `policy.yaml` nor its `.sig` is in `MANIFEST.sha256`.

**Reproduction:**

```sh
rm governance/policy.yaml.sig
# then edit the file the guards consume:
#   budget_envelopes.M4: 0 -> 100000
#   external_surface.publishing: forbidden -> allowed
#   spot_check.sample_rate_k: 3 -> 0
sed -i 's/^  total: 0.*/  total: 5000/' budget.yaml     # now within the raised envelope
uv run python scripts/check_manifest.py && bash scripts/custodian.sh --check-only
```

Observed:

```
check_manifest: OK — frozen paths intact; tier-c.yaml consistent with the guards
custodian: frozen-path hashes verify
custodian: policy.yaml unsigned (expected before the opening sitting)
custodian: custody floor intact
```

`check_manifest`'s spend-envelope check passes because it compares `budget.yaml`
ceilings against `max(policy envelopes)` — and the envelope was just raised in the same
edit. Tier-C door 1 (`spend-envelopes`) and door 2 (`external-bytes`) both walked
through, with the custodian printing *"custody floor intact"*.

**This directly falsifies a premise the repo is currently relying on.** D0048's proposal
(`docs/proposals/2026-08-24-policy-in-repo-mechanics.md`, committed today) states:

> `governance/policy.yaml` is owner-signed ... and the custodian verifies that signature
> on every run, so the builder cannot edit it — any edit invalidates the signature.

True only while the signature is *required* to exist. It is not.

**Severity: high.** Every Tier-C value that lives in policy becomes builder-editable,
including `sample_rate_k`, which is what decides how much of the record set the owner
ever sees (RT-11).

**Exploitable by accident?** Unlikely, but a plausible near-miss: a `.gitignore`
covering `*.sig`, or a clean/rebase that drops an untracked signature, produces the same
state and no guard complains.

**Closure:** `check-manifest-unsigned-policy/` plus the custodian check-4 patch. Both
drafted; the same `OWNER_SIGNED` list should carry `MANIFEST.sha256` (RT-01).

## RT-05 — Evidence is unauthenticated: `tannen laws report` can be made green without running anything. **High.**

**Claim.** The evidence store is content-addressed, not attested. Any process can write
a schema-valid `verdict: "pass"` record carrying the law's current descriptor, using the
repo's own public API. The report matches on descriptor and verdict; it has no notion of
who produced a record or whether any test ran.

**Reproduction** (with L0.6 genuinely failing — the mutating `gc()` from RT-01, no
conftest, evidence store emptied first):

```python
from pathlib import Path
from tannen.laws.discovery import discover_laws, implementation_subject, law_descriptor, milestone_label
from tannen.laws.evidence import EvidenceStore, build_record

root = Path(".").resolve(); store = EvidenceStore(root); subject = implementation_subject(root)
for law, modules in discover_laws(root, "m0").items():
    store.put(build_record(law_id=law, milestone=milestone_label("m0"), verdict="pass",
                           descriptors=[law_descriptor(root, law, modules, subject=subject)],
                           seed="hypothesis-derandomize"))
```

```
forged 10 passing records; no test was executed
$ uv run tannen laws report
L0.6    ok      pass     hypothesis-derandomize    2026-08-24T14:27:45.444699+00:00 ...
OK — 10 law(s) carry fresh passing evidence.
EXIT=0
$ TANNEN_NO_EVIDENCE=1 uv run pytest tests/laws/m0/test_l0_store.py -q
FAILED tests/laws/m0/test_l0_store.py::test_l0_6_gc_refuses
1 failed, 8 passed
```

**Why it matters even though `make verify` also runs pytest.**

1. `uv run tannen laws report` is CLAUDE.md's stated done-criterion for an
   implementation session ("implementation is done when ... `tannen laws report` shows
   fresh evidence for every law"), and it is quotable on its own.
2. `evidence/` is gitignored (D0041), so **nothing about the report is auditable from
   git history**. A reviewer with the repo cannot check any freshness claim.
3. The digest — the owner's only view — reads the same store.
   `scripts/gen_projections.py::laws_section()` calls `build_report(root, None)`; I
   rendered it in-process against an emptied store and got
   `**M0**: 0/10 law(s) carry fresh passing evidence`. Against the forged store it
   reports 10/10. The owner's digest would state the forgery as fact.
4. `TANNEN_EVIDENCE_ROOT` is read by *both* the plugin and the report, so the whole
   store can be relocated to a prepared directory with one exported variable.

**Severity: high.** BRIEF P6's evidence stream is the substrate for graduated autonomy
(§9.2); a forgeable stream widens defaults on invented evidence.

**Exploitable by accident?** No. But an *honest* variant is reachable by accident: a
stale `evidence/` directory carried across a `git checkout` can make the report green
for code that this run never exercised, whenever `src/tannen` happens to hash the same.

**Closure:** no poison fixture (see the fixture README's last section). Two `Makefile`
lines: run pytest and the report under a freshly removed
`TANNEN_EVIDENCE_ROOT=$PWD/.verify-evidence`, so the gate's report can only see records
the gate's own run produced.

## RT-06 — Tier C's "affirmative owner signature only" is enforced by nothing, and a Tier-C record can be invisible in the digest. **High.**

**Claim.** `tier: C` is an enum value in a YAML file the builder writes. No guard
requires a signature, and `gen_digest` surfaces Tier-C records **only** when their
effective status is `blocked-on-owner`. A Tier-C record that says `accepted` appears in
no section of the digest at all.

**Reproduction** (throwaway clone, not the real `decisions/`):

```yaml
id: D0050
title: Adopt the standard build-metadata helper
tier: C
date: "2026-08-24"
decision: >-
  Publish the M0 evidence stream to a public S3 bucket for the M1 differential
  harness, and take a dependency on the Renavon monorepo's ref helpers.
status: accepted
bindings:
  - type: file
    target: BRIEF.md          # resolves; enforces nothing (RT-10)
```

`check_decisions --today 2026-08-25` reports only `DECISIONS.md is stale` (which
regenerating fixes); the record itself is accepted. Rendering `gen_digest` in-process:

```
## Requires owner (Tier-C queue ...)
- **All spend envelopes/ceilings are zero** — ...
- **D0047** M0 close is a milestone boundary ...
## Risk-flagged decisions (always shown)   [22 records, none of them D0050]
## Spot-check sample (K=3 ...)             [D0002, D0006, D0007]
D0050 mentioned in digest? False
```

Two doors (`external-bytes`; and BRIEF §10's "No dependency on the Renavon monorepo")
walked through, with the owner's exception-only view showing nothing.

**Severity: high.** BRIEF §9.2 makes Tier C the load-bearing distinction of the whole

**Exploitable by accident?** Partly. A builder who genuinely believes a record is Tier A
and mis-files it gets the same invisibility for free — and the *sampling* is what is
supposed to catch mis-tiering, which brings us to RT-11.

**Closure:** `check-decisions-unsigned-tier-c/` plus the `gen_projections` patch that

## RT-07 — The ratchet's baseline is an unvalidated comment in an unmanifested file. **High.**

**Claim.** `previous_metrics()` reads `<!-- metrics: unenforced=N residue=M -->` out of
the most recent `digest/*.md` strictly older than today. Digest files are not in
`MANIFEST.sha256`, and — unlike `CONCEPTS.md` and `DECISIONS.md` — **no guard ever
verifies a digest's `input-hash` header**. `read_header_hash` is called for those two
projections only.

**Reproduction:**

```sh
$ sed -i 's/<!-- metrics: unenforced=2 residue=5 -->/<!-- metrics: unenforced=99 residue=99 -->/' digest/2026-08-24.md
$ uv run python scripts/check_decisions.py --today 2026-08-25
  ratchet: unenforced=2 (was 99), residue=5 (was 99), baseline digest 2026-08-24
check_decisions: OK — 47 records valid; ...
```

Deleting the digest works too — `ratchet: ... (no earlier digest to ratchet against)`,
guard silent. And since `check_ratchet` never verifies the digest is generated, a
hand-authored digest is also a forged owner-view artifact.

**Also observed, and worth the owner knowing:** on 2026-08-24 there is **no baseline at
all**. `digest/2026-08-24.md` is the only digest and `previous_metrics` requires
`stem < today`, so today's run prints `no earlier digest to ratchet against`. That is
the documented design (a rise must be seen before it becomes a baseline) — but it means
the ratchet's first live day is the day *after* a digest is written, and a session that
writes and reads a digest on the same day is unratcheted.

**Severity: high.** BRIEF §9.1 point 4 makes the two ratcheted metrics the owner's
quantitative handle on drift.

**Exploitable by accident?** Yes, in one direction: deleting or renaming a digest file
during housekeeping removes the baseline and no guard says a word.

**Closure:** `check-decisions-ratchet/` (pins that the ratchet still fires — D0047 asks
for exactly this), plus: verify digest header hashes the way `CONCEPTS.md` /
`DECISIONS.md` are verified, and give `digest/` manifest rows or an owner signature.

## RT-08 — `TANNEN_CHECK_DECISIONS_NESTED` in the ambient environment disables all 15 pytest bindings, and the guard still says "green". **High.**

**Claim.** The escape hatch is a plain inherited environment variable. Set anywhere in
the calling environment, it makes `resolve_pytest_bindings` return "no problem" for
every target, and `Failures.finish` then prints `N pytest binding(s) green` for
bindings that were never resolved.

**Reproduction** (an existing record's pytest binding pointed at a non-existent node):

```
$ uv run python scripts/check_decisions.py                       # EXIT=1
  - decisions/0044-ratchet-hardened.yaml: binding does not resolve —
    pytest node does not collect: tests/test_governance_ratchet.py::test_this_node_does_not_exist_at_all

$ TANNEN_CHECK_DECISIONS_NESTED=1 uv run python scripts/check_decisions.py
  pytest bindings: 15 not re-resolved (nested run; the outer run enforces)
  [the dead binding is not reported at all]
```

And on the unmodified tree the summary line under the hatch reads, verbatim:

```
check_decisions: OK — 47 records valid; 15 pytest binding(s) green; ...
```

**Severity: high.** 15 of the repo's enforcement bindings — the mechanism that makes
decisions load-bearing — turn off from outside the repo, with a green line claiming
otherwise.

**Exploitable by accident?** Yes, and this is the most likely accident in the whole
report: a builder who exports the variable once while debugging the recursion, or puts
it in a shell profile, silently loses binding enforcement for every later session.

**Closure (be honest about the limit):** an inherited environment signal cannot be
authenticated — any nonce a parent passes is equally settable by whoever launched the
parent. What *is* closable: (1) clear the variable at every top-level call site
(`env -u TANNEN_CHECK_DECISIONS_NESTED …` in `Makefile`, `.pre-commit-config.yaml`,
`custodian.sh`), which removes the accidental case entirely and makes the deliberate
case a visible diff; (2) stop calling unresolved bindings "green". Fixture:
`check-decisions-nested-hatch/` (bites today, and pins the pytest-binding tooth the
corpus currently has no fixture for).

## RT-09 — The law descriptor does not address the harness, so evidence survives the harness being weakened. **Medium-high.**

**Claim.** `implementation_subject()` hashes `(root/"src"/"tannen").rglob("*.py")` minus
`__pycache__`. Its docstring says the subject is "deliberately the whole of
`src/tannen`" so that "an edit elsewhere" cannot "silently inherit an old verdict". But
what decides *how hard a law was tested* is not in `src/tannen`.

**Reproduction** — each of these leaves all ten M0 descriptors byte-identical:

```
non-.py file added to src/tannen   -> descriptors unchanged: True
conftest.py law harness weakened   -> descriptors unchanged: True   (max_examples=1)
new conftest.py in frozen law dir  -> descriptors unchanged: True
pyproject dependency pin changed   -> descriptors unchanged: True   (hypothesis pin)
CONTROL: src/tannen/*.py changed   -> descriptors unchanged: False
```

So evidence earned under `derandomize=True` with full Hypothesis budgets stays "fresh"
after the profile is cut to one example; a data file the implementation reads is outside
the subject entirely; and the RT-03 conftest is invisible to freshness. The record's
`environment.packages` *does* capture pytest/hypothesis versions, but `build_report`
never compares them to anything — it matches on descriptor alone.

**Severity: medium-high.** It does not by itself break a law; it breaks the claim
freshness makes.

**Exploitable by accident?** Yes — tuning the Hypothesis profile is normal work and
carries no signal that it invalidated nothing.

**Closure:** widen `implementation_subject` to include `conftest.py`, `pyproject.toml`,
any `tests/laws/**/conftest.py`, and non-`.py` files under `src/tannen`. Draft in the
fixture README. Note it moves every descriptor on landing — do it at the *start* of M1,
not at the boundary.

## RT-10 — Bindings can resolve without enforcing, so the unenforced count is satisfiable by pointing at anything. **Medium.**

**Claim.** `binding_violation` asks only whether a target *exists* / *resolves* /
*collects and passes*. Nothing relates the target to the decision. A record bound to
`file: BRIEF.md` is "enforced" and drops out of the unenforced count.

**Reproduction:** D0050 in RT-06 above, bound to `BRIEF.md` — `check_decisions` accepts
it and the ratchet's `unenforced` stays flat. Same holds for `config:` bindings (a key
that resolves in a *neutered* `pyproject.toml` contract still resolves — RT-02 (a) leaves
`tool.importlinter.contracts` intact) and for `pytest:` bindings to a test that passes
without touching the decided behaviour.

**Severity: medium.** It is the pressure-relief valve for the ratchet: debt can be made
to fall without anything being enforced.

**Exploitable by accident?** Yes — binding to "the file this is about" rather than "the
artifact that enforces this" is an easy, well-meant mistake, and the guard rewards it.

**Closure:** no fixture proposed (a guard cannot judge relevance). The reviewable
mitigation is to make the digest print each binding's `detail` field for records added
since the last digest, so the owner reads the claim rather than the count.

## RT-11 — Digest invisibility is compositional: tier, risk flags and K are all builder-side. **Medium.**

**Claim.** The exception-only digest shows (i) `blocked-on-owner` Tier-C records,
(ii) records carrying `risk_flags`, (iii) K sampled records. All three inputs are under
builder control:

- `tier` and `risk_flags` are fields the record's author writes; neither is checked
  against the record's content.
- `sample_rate_k` is read from `governance/policy.yaml` — editable via RT-04.
  `sample_rate_k: 0` empties the sample section.
- Even untouched, K=3 over the current 27 unflagged records (49 records, 22 carrying
  `risk_flags`) gives any single record a ~11% chance of being sampled. Sampling is not
  a deterrent against one deliberately mis-tiered record.
- The digest renders only `title` for flagged records and only the first line of
  `decision` for Tier-C queue items, so a bland title carries a lot.
- The seed is `input_hash(decisions) ^ date`; adding whitespace to any record re-rolls
  the sample, so an unlucky draw is re-rollable at zero cost. *(Reasoned, not
  brute-forced — see S-04.)*

Demonstrated end-to-end by D0050 in RT-06: absent from all three sections.

**Severity: medium** on its own; it is the *amplifier* that makes RT-06 matter.

**Closure:** surface all Tier-C records unconditionally (RT-06 patch); consider deriving
`risk_flags` mechanically from the record's bindings and text (e.g. any record touching
`governance/`, `budget.yaml`, `allowed_signers`, `MANIFEST.sha256` is auto-flagged
`governance-paths`) rather than trusting the author's self-assessment.

## RT-12 — Decision records are declared append-only; nothing enforces it. **Medium.**

**Claim.** BRIEF §9 and D0045 treat records as append-only event records whose text is
immutable ("bindings are mutable, decisions are not"). No guard compares a record
against git history, no record is hashed into a chain, and none is signed. Editing a
past record's `decision`, `tier`, `status`, `risk_flags` or `bindings` passes every
check once `DECISIONS.md` is regenerated.

**Reproduction:** observed twice as a by-product — editing D0044's pytest binding target
(RT-08) and adding D0050 (RT-06) both produced exactly one violation,
`DECISIONS.md is stale (input-hash mismatch)`, which `make projections` clears. The
record content itself is never questioned.

Concretely composable with RT-01: delete D0022's `type: manifest, target: BRIEF.md`
binding, then delete `BRIEF.md`'s manifest row, then edit BRIEF.md. Three edits, all
guards green.

**Severity: medium**, rising to critical in composition with RT-01.

**Exploitable by accident?** Low — but "fixing a typo in an old record" is a natural
thing to do and is exactly the act the rule forbids.

**Closure:** in `check_decisions`, compare each record against its blob at the commit
that introduced it (`git log --diff-filter=A --format=%H -- <path>` then
`git show <sha>:<path>`), allowing only additions to `bindings` and `links` (D0045).
Fixture would need a git repo, like `custodian-close-tag/`; not drafted.

the five Tier-C doors, the `guard_enforced` list, the BRIEF §10 non-goals and the

## RT-14 — The poison corpus has one tooth per guard; the guards have many, and the guards are unfrozen. **Medium.**

**Claim.** Each fixture proves one specific code path in one guard still fails. Every
other path in that guard can be weakened without the custodian noticing — and
`scripts/check_manifest.py`, `check_concepts.py`, `check_decisions.py`, `_gov.py` and
`gen_projections.py` are **not** in `MANIFEST.sha256`, so weakening them is a normal
builder edit.

What each fixture actually covers, and what it leaves uncovered:

| Fixture | Covers | Does not cover |
|---|---|---|
| `check-manifest/` | hash mismatch on a listed path | `--staged` mode; the D0034 git-tracked rule; the whole `check_tier_c_consistency` block (budget-vs-envelope, D0016 coverage); row deletion (RT-01) |
| `check-concepts/` | snapshot ≠ recorded sha256 | orphan artifacts; grade-S vector corpora; `[owns]`/`[cites:]` markers; `CONCEPTS.md` freshness; duplicate ids |
| `check-decisions/` | a `file` binding target that is absent | schema validation; id ↔ filename; `pytest`/`config`/`manifest` bindings; the ratchet; veto clocks; receipt state; `DECISIONS.md` freshness |
| `lint-imports/` | that import-linter runs | anything about tannen's contracts (RT-02) |

A worked example of the shape: an exclusion added to `check_frozen_files` for one real
path leaves the fixture (which contains only `poisoned.txt`) failing exactly as before.
That one is caught in practice — `custodian.sh` step 1 runs `sha256sum -c
MANIFEST.sha256` independently — but there is no such independent second check behind
`check_concepts.py` or `check_decisions.py`.

**Severity: medium**, and it is the reason every other finding survives the custodian.

**Closure:** the five fixtures drafted here roughly double the corpus (adding the
ratchet, pytest-binding, sealed-path, custody-signature and Tier-C-signature teeth). The
structural fix beyond that is to give `scripts/*.py` manifest rows, so weakening a guard
is at least a frozen-path violation.

## RT-15 — Deleting tags erases the trust root, the delegation clock and the consent clock, and every guard stays green — including the one that landed today. **High.**

**Claim.** No guard requires any tag to exist. Deleting them is a local, unsignable,
untracked operation that removes the pin `check_tag_signers.py` was just written to
enforce, empties the `bless_epoch` that the D0036 ordering rule depends on, and makes
the attention receipt fresh for ever.

**Reproduction, run against `ca48a8b` (a throwaway clone), i.e. *after*
`scripts/check_tag_signers.py` joined `make verify`:**

```
$ uv run python scripts/check_tag_signers.py                    # baseline
  trust root: brief-freeze pinned at c219e63819be…
  brief-freeze: owner@tannen (class role: owner)
  m0-laws-freeze: builder@tannen (class role: builder)
check_tag_signers: OK — 2 tag(s); every signer matches its tag class     EXIT=0

$ git tag -d brief-freeze m0-laws-freeze
$ uv run python scripts/check_tag_signers.py
  trust root: brief-freeze does not exist yet (nothing to pin)
check_tag_signers: OK — 0 tag(s); every signer matches its tag class     EXIT=0

$ bash scripts/custodian.sh --check-only
custodian: custody floor intact                                          EXIT=0
```

`check_trust_root` treats an absent `brief-freeze` as "not created yet", which is the
right reading for a fresh repo and the wrong one for a repo that has been through its
opening sitting. `custodian.sh` check 3 iterates `git tag -l`, so an empty tag set is
vacuously fine and `bless_epoch` stays empty — which switches off the
delegation-precedes-signature check for every tag created afterwards.

**And the consent clock.** `receipt_state()` returns fresh whenever no boundary tag
postdates the receipt. Verified in the same clone, with the tags gone:

```
boundary tags: []
2026-08-25 (True, 'receipt 2026-08-24.md fresh (no milestone boundary since)')
2027-06-01 (True, 'receipt 2026-08-24.md fresh (no milestone boundary since)')
2030-01-01 (True, 'receipt 2026-08-24.md fresh (no milestone boundary since)')
```

So a stale receipt — the state that is supposed to block Tier-B consent and pause work
at the next boundary — is reversible with `git tag -d`. `boundary_tag_dates()` also
returns `[]` on any git failure or outside a repo (a tarball, an export), i.e. fresh.

**Severity: high.** It is the single act that neutralises the trust root, the
delegation-ordering rule and the presence measurement at once, and it is the
counterpart to today's D0050 work: that guard pins *which* object `brief-freeze` is,
and this finding is that it need not be any object at all.

**Exploitable by accident?** Yes, and unusually so: tags do not travel with
`git clone --depth`, they are dropped by some export and mirror workflows, and a
`git push` without `--tags` never carries them. A fresh working copy that simply lacks
the tags looks, to every guard, exactly like this attack.

**Closure:** make the tag set required rather than optional. In
`governance/tag-roles.yaml`, mark `trust_root` as **required once
`owner_key_enrolled(root)`** and have `check_tag_signers.check_trust_root` fail on
absence in that case; and add a `required_tags:` list (at minimum `brief-freeze` and the
`*-laws-freeze` tag of every closed milestone) that the guard asserts is present. A
poison fixture is a bare repo with the tags stripped — the same `repo.bundle` shape as
`custodian-close-tag/`, so the two share a generator. `governance/tag-roles.yaml`
itself still needs a manifest row (its header says it is "proposed for MANIFEST.sha256
... at the M0 sitting"); until it has one, RT-13 applies to it too.

# SUSPECTED (reasoned, or only partly reproduced)

## S-01 — A backdated boundary tag may be able to hold the receipt fresh.

`boundary_tag_dates()` reads `creatordate`, which `GIT_COMMITTER_DATE` sets, and the
D0036 ordering guard only rejects builder tags earlier than `brief-freeze` — both
`brief-freeze` and the receipt are dated 2026-08-24, so an intra-day window exists in
which a boundary tag would not count as "later than the receipt". **Not tested:**
creating tags was out of bounds for this pass. (The *deletion* half of this attack is
confirmed as RT-15.)

## S-02 — `git commit --no-verify` bypasses the pre-commit frozen-path hook.

`check_manifest --staged` runs only from `.pre-commit-config.yaml`. Not tested (it would
require committing). The default-mode check in `make verify` catches the result
afterwards, but only for paths that still carry a manifest row (RT-01).

## S-03 — There is no second execution of the gate anywhere.

`git remote -v` is empty and `.git/refs/remotes` does not exist, so `.github/workflows/ci.yml`
has never run. Stated in the preamble; listed here because I inferred rather than
observed that it has *never* run (there is no run history to inspect).

## S-04 — The digest sample seed is re-rollable.

`seed = int(input_hash(decision_paths, root)[:16], 16) ^ int(date)`. Any whitespace edit
to any record changes `input_hash` and therefore the draw. I did not brute-force a seed
that excludes a chosen record; with K=3 over 25 unflagged records the base rate already
makes the sample a weak deterrent, so the grind is unnecessary in practice.
