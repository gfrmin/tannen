## RT-M5-01 — `PYTHONPATH=.dogfood` lets two gitignored files rewrite the kill criterion's verdict at the law, evidence and report layer. **High.**

**The asymmetry.** The Makefile's `verify` runs every Python guard as `.venv/bin/python -I -P`.
That is the RT-02/RT-08 lesson: `-I` ignores `PYTHONPATH`, and the floor may depend only on paths
named literally (D0063 ruling 3). The pytest step is the exception. Since `8c46529` it runs with
`PYTHONPATH=$(DOGFOOD_PYTHONPATH)`, where `DOGFOOD_PYTHONPATH := $(CURDIR)/.dogfood` (`Makefile:41`,
`:48`); `laws-sweep` (`:70`) is wired the same way.

The reason for the wiring is sound: the vertical's pipeline must be importable by name, both in the
parent process and in L5.10's child interpreters. The effect is broader than the reason. **A
`PYTHONPATH` entry is searched for `sitecustomize` when every interpreter starts.** Anything placed
there runs before pytest, in every interpreter the gate's pytest step starts, and can use
pytest's own documented environment variable to load a plugin from the same directory.

**What `.dogfood/` is:**
- **gitignored** (`.gitignore:29`), so no diff, commit, hook, CI run or PII scan ever sees it;
- **present only on the owner's machine**, which by D0259 is the only place M5's laws run, so the
  only place M5's close can be attested;
- **written by builder sessions** (B2 wrote the vertical's module there, D0268 ask (6));
- **not checked by any guard** for what it contains beyond the corpus's own schema.

**The reproduction**, in a scratch clone with a synthetic `.dogfood/`:
- **The corpus:** three items with production outputs, `authorisation` naming the real signed
  D0268 (so L5.8 passes on its merits), and a measurement that selects it.
- **The pipeline:** writes and returns bytes that differ from production's, with no divergence
  recorded. L5.9 is built to fail on exactly this.

Two files were then added to `.dogfood/`, and nothing else changed:
1. **`sitecustomize.py`**, a two-line module. Python imports it automatically at interpreter
   startup because `.dogfood/` is on `PYTHONPATH`. Its only act is to set pytest's
   `PYTEST_PLUGINS` environment variable to the name of the second file.
2. **`_vertical_support.py`**, a pytest plugin loaded through that variable. It has one
   `pytest_runtest_makereport` hook wrapper that rewrites a failed report for any node whose id
   contains `test_l5_9_` into a pass.

No module was shadowed, and there was no `.pth` file and no `conftest.py`.

**The judges, with the Makefile's own pytest command over `tests/laws/m5` and a throwaway evidence
root:**

| | pytest | junit case for L5.9 | `tannen laws report --milestone m5` |
|---|---|---|---|
| **control**: wrong bytes, no divergence, `.dogfood/` holding only the corpus, store, measurement and pipeline | `1 failed, 123 passed`; FAILED `test_l5_9_…` | `<failure>` | `L5.9 failing fail`, `ok: False` |
| **attack**: the same tree plus the two files | `124 passed` | passed | `L5.9 fresh pass`, `ok: True` |

**Through the whole gate: RED, and caught incidentally.** The same two files, combined with
RT-M5-04's and RT-M2-02's attacks in one clone, went through the full `make verify`. It stopped at
the pytest step: `7 failed, 1393 passed, 1 skipped, 6 xfailed`, exit 2. All seven failures were
tests that start a child pytest with a `PYTHONPATH` of their own: the oracle-shadow poison tests in
`tests/test_governance_scripts.py`, and `tests/test_laws_runner.py::test_a_shadowed_oracle_module_is_refused`.
Each child inherited the environment variable the first file sets but not the directory on the path,
so it failed with `Error importing plugin "_vertical_support"`.

So the gate refused this form **for a reason unrelated to M5**: a side effect of how the plugin was
loaded, not any check of `.dogfood/` or of L5.9's verdict. This pass did not build a form without
that side effect, and does not claim the full gate passes one. It downgrades its own first-draft
Critical to **High** on that ground. What stands, measured, is that a file in `.dogfood/` executes
inside the gate's pytest process and can rewrite a law's verdict before evidence, junit and the
laws report read it, while no guard inspects that directory.

**Why the evidence plugin does not save it.** `tannen.laws.plugin` builds its verdict in
`pytest_runtest_logreport` from the report object. The rewrite happens one hook earlier, in
`pytest_runtest_makereport`, so the evidence record carries the forged verdict. The same object
feeds junit, so `check_decisions --pytest-report` reads the forgery as well.

**For the builder's remedy, answering its question.** The owner's real `.dogfood/` holds, by
filename, only the vertical's and the corpus builder's modules, with no `sitecustomize`, `.pth` or
shadowing module. So the finding is the **reachable surface**, not an observed compromise. Any of
the following, placed in `.dogfood/`, runs inside the gate's pytest process:
- a `sitecustomize`/`usercustomize` module;
- a module named after anything imported later that does not come from the venv first (which is the
  reason the vertical is importable at all);
- a pytest plugin named by `PYTEST_PLUGINS`.

`.pth` files are *not* processed from a `PYTHONPATH` entry (only from site directories), so they
are not a channel here.

**Remedy direction (not landed).**
- Put no directory on the gate's path. Import the vertical from its file location, the way
  `_dogfood_bind` loads frozen helpers, and hand L5.10's children the same file path.
- Alternatively, have a guard refuse any `.dogfood/` entry other than an enumerated set, and run the
  gate's pytest with `-p no:` / `PYTEST_DISABLE_PLUGIN_AUTOLOAD` plus an explicit plugin list.
- Either way the remedy touches frozen L5.10's child-interpreter contract (it reads the vertical by
  module name), so the likely home is a superseding law. It is a decision for the close sitting, not
  a builder one-liner.

**Freeze/custody:** the Makefile has been outside custody since D0267. `.gitignore` is outside it
too. L5.9 and L5.10 are frozen. No poison fixture covers the gate's environment.

## RT-M5-02 — The M5 laws judge bytes, and nothing ties the bytes to tannen. **High.**

M5's charter is "one Renavon vertical, byte-identical vs production" (BRIEF §8), and the point of
that is that **tannen** produces the bytes. The laws take the corpus's `pipeline` as an opaque
`MODULE:CALLABLE`. `dogfood.run` imports it and accepts any content address it returns
(`dogfood.py:136–162`). L5.9 compares that output's bytes with production's, and L5.10 checks that
fresh interpreters return the same refs.

Nothing asks whether the callable ran any tannen operator, built a `Rel`, or touched the kernel. The
one structural guard on the pipeline, `tests/test_dogfood_cross_repo.py`, scans the pipeline
module's **module-level** import closure for constellation packages. By design it does not descend
into function bodies (`:77`), and it does not look at processes.

**The reproduction.** Same scratch-clone harness as RT-M5-01. The corpus is three synthetic items.
A synthetic "production parser" (a five-line CSV-to-JSON function) produced the production outputs
and was also placed in `.dogfood/` as a module named `renavon`, a name on the `no-cross-repo`
forbidden list. Each pipeline below was installed as the corpus's `pipeline`. Then
`tests/laws/m5` and `tests/test_dogfood_cross_repo.py` were run with `PYTHONPATH=.dogfood`:

| Pipeline | Result |
|---|---|
| **control 1**: writes wrong bytes, no divergence recorded | `1 failed, 127 passed`; FAILED L5.9 |
| **control 2**: `import renavon` at module level, parses with it | `1 failed, 127 passed`; FAILED the cross-repo test |
| **V1**: reads the corpus file at import and returns each item's `production_output` ref unchanged; computes nothing | **`128 passed`** |
| **V2**: control 2 with the import moved inside the function body | **`128 passed`** |
| **V3**: runs the synthetic parser's source in a child Python process and stores its stdout | **`128 passed`** |
| **V4**: a pipeline whose every output differs, with every divergence recorded as `tannen-defect` and a one-line analysis | **`128 passed`** |

All four are **zero skips**, which is D0259's completion condition. V2 and V3 bring a
constellation parser into the vertical while the cross-repo guard stays green. V1 shows the laws
cannot tell tannen from an echo. V4 shows the charter passes a vertical that reproduces nothing, as
long as each miss is labelled. The spec's kill criterion forbids classifying "to make it go away",
but that rule is prose; no law bounds how many items may diverge.

**Why this matters beyond hygiene.** D0270 ruling (1) already records that M5, as built, "attests
that tannen reproduces production's code". This finding is that the laws do not attest even that
much: they attest that *some* callable reproduces it. Whether the real vertical is honest is a
question this pass was not permitted to look at. The finding is that **no gate asks it**.

**Remedy direction (not landed).**
- A law that the vertical's output is produced by a tannen graph: for example, `run` executing a
  `Built` returned by the pipeline through the executor, with its descriptor and operators recorded
  in the evidence. L5.4's measured operator set could then be compared with the operators that
  actually ran.
- A cross-repo scan that descends into function bodies, and a process rule over the pipeline module,
  both of which `check_doorway.py` already implements for `src/tannen`.
- A bound on non-identical items, or at least a count surfaced in the close digest.

All of these are superseding laws. **Freeze/custody:** L5.9 and L5.10 are frozen;
`dogfood.py` and the cross-repo test are unfrozen and uncustodied.

## RT-M5-03 — The derived doorway has three static evasions, and L5.1/L5.2 never run in CI. **High.**

L5.2 (frozen) and `scripts/check_doorway.py` (the guard it restates) closed RT-M4-02's two named
holes, and both are confirmed closed below. Their stated limits are:
- dynamic imports;
- code the interpreter did not ship;
- `ctypes`/`cffi`.

Three evasions fall **outside** those limits. Each was planted in turn at the end of
`src/tannen/store.py` in a scratch clone, then judged by `check_doorway.py`, `lint-imports`
(`governance/importlinter.toml`), and L4.9 + L5.2 run together.

| Payload in `tannen.store` | check_doorway | lint-imports | L4.9 + L5.2 |
|---|---|---|---|
| **control**: `import os` and an `os.system` call | RED `process — tannen.store uses os.system` | green | `1 failed, 12 passed` |
| **control**: `import imaplib` | RED `network — tannen.store imports imaplib` | green | `1 failed, 12 passed` |
| **(a)** `import os as <alias>` and `<alias>.system(...)` | **green** | green | **`13 passed`** |
| **(b)** `import webbrowser` and `webbrowser.GenericBrowser([<argv>]).open(url)` | **green** | green | **`13 passed`** |
| **(c)** a new module under `tannen/laws/` that imports `xmlrpc.client` and makes a call, imported by `tannen.store` | **green** | green | **`13 passed`** |

Each evasion was then confirmed live outside the repo, with no network:
- (a) ran a child process;
- (b) ran an arbitrary argv, with `echo` as the stand-in;
- (c) attempted a TCP connect to a refused loopback port (`Connection refused`).

**Mechanisms:**
- **(a)** The process rule matches only an attribute on a `Name` spelled literally `os`
  (`check_doorway.py:251`, `test_l5_2 … :237`).
- **(b)** `webbrowser`'s closure reaches `subprocess` but not a socket, and `webbrowser` is not in
  `PROCESS_MODULES`. The process rule is **not** derived the way the network rule is: it is
  refused by name, and the name list is `{subprocess, multiprocessing, pty}`.
- **(c)** Both judges skip every import whose top-level name is `tannen` (`check_doorway.py:282`,
  L5.2 `:254`). `tannen.laws` is a network door "for the runner", but it is a package that anyone
  can add a module to, so any shell module can reach the network through it.

**And L5.1/L5.2 never run in CI.** They carry the M5 sentinel (the corpus must be present), so on
CI both are skipped. CI run 35419635219's report reads "M5: 10 law(s) are frozen ahead of their
implementation and have no evidence yet". RT-M4-02 was closed at D0271 because L5.2 "passed live
with fresh evidence on the owner's machine". That is true, but on every push the doorway's only live
judge is the unfrozen, uncustodied `check_doorway.py` (see RT-M5-05). L5.1 and L5.2 are
self-contained: neither needs the corpus. Gating them behind it was D0259's choice to keep "all ten
live together", and the cost is that the CLI clamp and the doorway have no frozen judge in CI.

**Remedy direction.**
- Derive the process set the way the network set is derived, from a closure reaching `_posixsubprocess`,
  `posix.fork*`/`exec*`/`spawn*` and `os.system`.
- Resolve aliases of `os`.
- Make the runner door a list of modules, not a package prefix, or scan tannen-internal imports into
  the door.
- For CI: a superseding law file for L5.1/L5.2 without the corpus sentinel.

**Freeze/custody:** L5.2 is frozen; `check_doorway.py` is outside custody since D0267. The
`doorway-network-residue` fixture carries none of the three payloads.

## RT-M5-04 — `check_decisions` resolves every xfail as a strict retirement: one line disarms an enforced binding. **High.**

D0266 made the gate's `check_decisions` read pytest's junit report (`--pytest-report`), and
`31a3476` fixed its classification. pytest writes a strict xfail as
`<skipped type="pytest.xfail">`, which had been read as an unexplained skip. The fix classifies
**every** `type="pytest.xfail"` case as a retirement, and `report_violation` resolves a binding
whose live cases are all xfails as enforced (`check_decisions.py:370–372`).

junit carries no strictness, reason or registry origin, so it cannot tell three things apart:
- a D0128 retirement: strict, registered in `governance/laws.yaml`, whose node must fail;
- a non-strict `@pytest.mark.xfail`;
- an imperative `pytest.xfail()` call inside a test body.

The default mode has the same hole in text form: `-rs` prints no line for an xfail and the exit
code is 0. That is RT-M2-02's fourth leg ("`pytest_violation` rejects skips but says nothing about
xfails"), which was never closed and has now been carried into the new mode.

**The reproduction**, in a scratch clone, on the binding D0271 wrote for RT-M4-03's fix
(`tests/test_export_door.py::test_a_serve_label_over_wider_operators_is_refused`, enforced).
`check_decisions.resolve_from_report` was run over each report:
- **clean tree:** `2 passed`, and the binding resolves.
- **control 1:** RT-M4-03's five-line check deleted from `export.py`. `1 failed, 1 passed`, and
  the binding is RED: `pytest node fails: … (failure)`.
- **control 2:** fix deleted, and `pytest.skip("flaky on CI")` added as the test body's first line.
  junit has `<skipped type="pytest.skip">`, and the binding is RED:
  `pytest node is skipped (a skipped binding is not enforcement)`.
- **attack:** fix deleted, and `pytest.xfail("flaky on CI")` added as the first line instead.
  `1 passed, 1 xfailed`; junit has `<skipped type="pytest.xfail">`. **The binding resolves green.**
- **variant:** a non-strict `@pytest.mark.xfail(reason=…)` decorator instead of the call. Green in
  `--pytest-report` mode, and green in the default mode too.

**Scale.** 194 enforced pytest bindings across 118 records; **138 of them target unfrozen tests**
(23 files). Each can be disarmed this way, by the same edit that would reveal a regression.

**Through the whole gate.** See the addendum: a full `make verify` over this attack together
with RT-M2-02's, without RT-M5-01.

**Remedy direction (builder-landable, D0092 binding with it).** Treat an xfail case as a
retirement only if its node is in `governance/laws.yaml`'s `superseded` list (which conftest
reads). Any other xfail is resolved like a skip. Add a poison fixture carrying an imperative xfail
on a bound node. **Freeze/custody:** `check_decisions.py` is outside custody since D0267. The
`check-decisions-nested-hatch` and `check-decisions-file-skip` fixtures carry skips, not xfails.

## RT-M5-05 — D0267's custody shrink: a guard narrowed to pass a real-tree breach while still failing its poison, with the full `make verify` green. **Medium.**

- the generators and the sitting drivers.

The stated premise (`governance/tier-c.yaml:115`) is that "their liveness is proved by the
custodian's poison matrix at every gate, in seconds, and audited by the boundary red team". This is
that audit. **A poison fixture proves a guard still has one tooth. It does not prove the guard

now in force for every one of these guards again.

**The reproduction**, in a scratch clone:

- **The narrowing:** `tannen.store` added to `PROCESS_DOORS` in `scripts/check_doorway.py`.
- **The adjustment:** one row of the unfrozen `tests/test_check_doorway.py` parametrisation moved
  from `store.py` to `executor.py`. That row plants `import subprocess` in `store.py` and expects it
  caught; the narrowing made it the only test that noticed (`1 failed, 51 passed` before the move).

In total: three files, 8 insertions, 2 deletions.

**Judges:**

- `check_doorway.py` over its poison fixture: **still FAILs, five violations**. The fixture's

The gate's own output names the widened door, and nothing reads that line. A second, cheaper form

**Severity Medium, not High:** it needs a builder edit to a guard, which is visible in review and in
`git log`. D0267 ruling 3 made CI, not review, the gate, and this is a case CI passes.

**Remedy direction.** Make each guard's positive control include the real tree's shape:

## RT-M5-07 — `measure_dogfood_candidates.py` counts block-comment lines. **Low.**

The frozen `loc/1` counter is "non-blank physical lines that are not only a comment"
(docs/specs/m5.md §2). `count_loc` drops a line only if its stripped text starts with the
extension's **line**-comment marker, and it states that "Block comments are not addressed by the
spec and are not addressed here" (`:80`). But a line inside a block comment *is* only a comment, so
the spec does address it.

**Answering the builder's question on what is over-counted:**
- **`/* … */` and `/** … */` blocks** in every `//`-family language (JS/TS/Go/Rust/Java/Kotlin/
  Swift/C/C++). Every line of the block counts except any line that happens to start with `//`.
  - Measured: a six-line JSDoc-style function in `.ts` (four comment lines, three code lines)
    counts **7**; `loc/1` says 3.
  - Control: a `.py` file with a `#` comment line and two code lines counts **2**, which is correct.
- **Lua `--[[ … ]]`**: the inner lines count.
- **Python docstrings and other triple-quoted strings are NOT over-counted under `loc/1`'s letter.**
  They are string expressions, not comments, so counting them is correct by the spec as written.
  Whether they *should* count is a spec question, not this finding.

**So does the owner need to re-measure?** Only if a candidate's `parser_files` include a
`//`-family or Lua file with block comments. The number counted wrongly is the block comments'
line count in those files. For an all-Python candidate set, this defect does not move the numbers.
This pass did not see the real measurement and does not know the candidates' languages.

**Remedy:** strip block comments per extension before counting, or refuse extensions with block
comments until it does. Unfrozen, builder-landable. The rest of the script held up. It refuses a
duplicate source, an unknown operator, a shape outside the frozen schema, and an unknown extension.
Its preview agreed with the frozen model on a two-candidate synthetic measurement.
