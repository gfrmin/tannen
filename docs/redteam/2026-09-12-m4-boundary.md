## RT-M4-01 — The SpendGuard fold trusts a shared, caller-writable store, so the ceiling is not enforced against the party it guards. **High** (inert today).

`SpendGuard`'s admission is a fold over the store, not a counter (docs/specs/m4.md §4, L4.5).
`spent()` (`src/tannen/oracles/context.py:99`) reaches every object that decodes to a tagged
value (`_tagged`, `:76`), keeps the `reservation/1` and `capture/1` values, and trusts their
structural agreement: a capture counts against a reservation iff it names it and agrees on
`(kind, oracle, input_key, scope, unit)`; a reservation with no settling capture contributes its
`worst_case`.

The store the fold reads is the same store the pipeline `tannen run` executes is handed. That
pipeline reaches it through the **public** `Oracles.store` property (`context.py:216`) and can
call `store.put_value(...)` with any tagged value it likes. **D0235(a) closed one half of this
exact hazard** — `Fetch.normalise` (`identity.py:262`) refuses a fetched body whose bytes decode
as a tannen value, "because the world never authors a tannen value." But the *pipeline* authors
them freely; nothing in the fold distinguishes a reservation or capture the `Oracles` context
wrote from one `put_value` wrote.

Two consequences, each reproduced from the failing side with a control. Both use an in-memory
budget with a nonzero ceiling (a mapping through `load_budget`, never `budget.yaml`, which stays
zero); the store is a throwaway directory; no transport reaches a network.

**(a) A price-0 capture erases a capture-less reservation's charge, defeating the ceiling.**
`spent()` computes, per reservation, `settled.get(ref, reservation["worst_case"])` — the sum of
settling captures' prices if *any* capture names it, else the worst-case fallback. The comment
says "a duplicate can only raise spend," and that is true for a reservation whose real capture
already wrote (captures sum). It is false for a reservation whose capture never wrote — the
transport raised, or the capture write failed, the case D0235(b)'s worst-case fallback exists to
charge. A pipeline plants a price-0 capture agreeing on `_SETTLES`, and `settled[ref] = 0`
*replaces* the worst case:

```
[1] transport raised; reservation stands, no capture
[1] honest fold spent(clock) = 5           (= worst_case fallback)
[1] CONTROL: a 6-cost call DENIED while worst_case stands:
    clock: spent 5 + worst case 6 against ceiling 10 usd in scope 'M4'
[1] ATTACK: after planting a price-0 capture naming the reservation, spent(clock) = 0
    → the same 6-cost call is now admitted (0 + 6 <= 10). The ceiling is defeated.
```

The planted capture carries empty `request`/`response` — the fold reads only `_SETTLES`, the
named `reservation`, and `price`. This path is conditional: it needs a reservation whose capture
failed. The next one is not.

**(b) A malformed reservation bricks a scope permanently.** Planting one `reservation/1` value
whose `worst_case` is not a non-negative integer makes `spent()` raise `SpendDenied` ("spend is
unknowable") for the *whole scope* — and the store is write-once, so it can never be removed:

```
[control] a clean scope admits a 1-cost call
[attack]  scope 'M4' is now PERMANENTLY unspendable (write-once store):
          SpendDenied: spend is unknowable: the store holds a reservation/1 value that lacks
          what the fold reads
```

This one is unconditional and irreversible. Any party with store-write access — the pipeline, or
any other session sharing the store (captures persist across sessions by design, §3) — can
render a spend scope dead forever, with no recovery path (BRIEF §10: no store mutation, ever).

**No authentication.** `_tagged` → `spent` decode and structurally check; there is no signature,
no provenance, no marker that a reservation/capture was minted by the `Oracles` context rather
than by `put_value`. The fold read values no oracle produced.

**Why this is beyond D0238, and why it is inert today.** D0238 (queued) is about *which budget a
caller names* — the authorisation the CLI hands SpendGuard. This is about *who can write the
ledger the fold reads* — the enforcement itself. D0240 ruled that "a budget file is an
authorisation, and authorisations are properties of the caller … SpendGuard's job is to enforce
the rule against whatever authorisation it is handed — and it does that correctly." The premise
of that ruling is that SpendGuard *does* enforce. RT-M4-01 is that it does not enforce against a
pipeline that also writes the store: the party a nonzero ceiling is meant to bound can subvert
the fold that bounds it. **Today this is entirely inert** — every ceiling in `budget.yaml` is
zero, `governance/policy.yaml`'s envelopes are zero, nothing here holds credentials for a real
transport, and no law or test reaches a network. The pre-budget sitting BRIEF §9.1 mandates is
exactly the moment a nonzero ceiling first arrives, and it is the right place for this.

**Remedy — a design question, not a one-liner (so: reported, not fixed).** `context.py` is
unfrozen and uncustodied, so a fix is builder-landable in principle. But making a reservation or
capture unforgeable in a content-addressed store the pipeline must *also* write to, without a
secret the pipeline does not hold, is a genuine design choice — a reservation namespace the
pipeline cannot write, a separate reservation store, or a signed fold — each with tradeoffs. It
belongs to the pre-budget sitting, with the D0092 regression binding written then. Frozen L4.5
(`tests/laws/m4/test_l4_spend.py`) constrains only the *honest* reserve-then-settle path driven
through the model's `Subject`; it asserts nothing about authenticating fold inputs, so an
input-authentication fix would not contradict it and would need no supersession.

**Freeze/custody:** `src/tannen/oracles/context.py` unfrozen and uncustodied; `test_l4_spend.py`
frozen. A poison fixture is premature — the guard that would enforce fold-input authenticity does
not exist yet, and a fixture belongs with the guard it poisons (RT-M3-02's lesson). A
fixture-candidate is drafted (see below) against the day the guard lands.

## RT-M4-02 — The doorway law L4.9 is a static scan over a hand-maintained network set, so a shell module reads the world with `make verify` green. **High.**

L4.9 (`tests/laws/m4/test_l4_doorway.py`, **frozen**) is M4's shell-side half of BRIEF §5.3 —
"the only IO doorway is `oracles/`, and the only way to read the world is through a capture
handle." It AST-scans every `src/tannen/**.py` for imports and forbids the network outside
`(tannen.oracles, tannen.r2)` and a clock outside `(tannen.oracles, tannen.laws)`.

The clock set is **derived** from `governance/importlinter.toml`'s `kernel-no-clock` contract
(`_derived_clock_set`) and carries a non-empty assertion. The network set is a **hand-written
literal** "named as residue" (`:48`) with no derivation and no completeness assertion — the
RT-M3-02 shape (an unasserted enumeration that lags), now living in a frozen law. Verified with
the law's own scanner (34 real modules scanned; live `violations()` empty for both sets, so the
tree passes legitimately and any pass below is a real pass):

```
NETWORK set: aiohttp asyncio boto3 botocore ftplib grpc http httpx requests smtplib
             socket ssl urllib urllib3 websocket websockets
imaplib      importable=True  in_NETWORK=False  scanned_as={'imaplib'}
poplib       importable=True  in_NETWORK=False  scanned_as={'poplib'}
socketserver importable=True  in_NETWORK=False  scanned_as={'socketserver'}
xmlrpc       importable=True  in_NETWORK=False  scanned_as={'xmlrpc'}
subprocess   ∩NETWORK=∅  ∩CLOCK=∅        (not scanned at all)
os           ∩NETWORK=∅                  (not scanned at all)
importlib.import_module('socket')  scanned_as={'importlib'}   (dynamic import invisible)
```

Three holes, in descending order of severity:

- **`subprocess` and `os` are not scanned at all.** `subprocess.run(["curl", url])` or
  `os.system("curl …")` in `tannen.store`, `tannen.executor`, `tannen.cli` or
  `tannen.incremental` reads the world outside the capture doorway, and **neither L4.9 nor
  `lint-imports` catches it.** `governance/importlinter.toml`'s `kernel-no-io` contract *does*
  forbid `subprocess`/`socket`/`urllib`, but its `source_modules = ["tannen.kernel"]` — it never
  scans the shell. The most natural way to read the world (shell out to `curl`) is entirely
  unguarded.
- **Live socket-opening stdlib modules are missing from the NETWORK set:** `imaplib`, `poplib`,
  `socketserver`, `xmlrpc.client` all import cleanly on 3.13 and open real sockets, and none is in
  the set. (`telnetlib`/`nntplib`/`smtpd` were removed in 3.12/3.13, so the set's omission of them
  is moot; the live ones are not.) A builder adding `import imaplib; imaplib.IMAP4(host)` to
  `tannen.store` passes L4.9.
- **Dynamic imports are invisible** (`importlib.import_module`, `__import__`). L4.9's docstring
  admits this, so it is reported as an *admitted* limitation, not a hidden one.

**Freeze/custody:** L4.9 is frozen (in `MANIFEST.sha256`), so it cannot be edited. Closing the
first two holes needs a **superseding frozen law** (a new file under `tests/laws/m4/` taking an
L4 id, the old one marked superseded in the manifest notes) that derives its forbidden set — the
way the clock set is derived — from a custody-set import-linter contract that also scans the
*shell*, not only the kernel. That contract is **exactly D0229 item (2)** ("the shell doorway
contract"), already queued and owner-key. So the remedy is: land the shell import-linter contract
(owner), then supersede L4.9 to derive from it (Session-A-shaped). A poison fixture is premature —
there is no shell contract yet to poison. A fixture-candidate note is drafted below.

## RT-M4-03 — The export door trusts a caller-set `.layer` and never re-derives it from `.operators`. **Medium.**

`export(store, built)` (`src/tannen/export.py:23`, L4.10) admits `built` iff
`built.layer is Layer.SERVE` and `output_ref is not None`, and reasons *from* the SERVE label *to*
"project and select only, so its provenance is trivially that of what it projects." But `Built`
(`executor.py:67`) is a `@dataclass(frozen=True)` with a **public constructor**, and `layer` and
`operators` are independent fields. `export` never checks that `layer_of(built.operators)` is
actually `SERVE`. A caller presents a SERVE label over a node that ran wider operators, and the
bytes leave:

```
layer_of({join, distinct}) = 3 (DERIVE)
CONTROL: an honest Built(layer=DERIVE, operators={join,distinct}) → refused: LayerError
FORGED : Built(layer=SERVE,  operators={join,distinct}) → EXPORTED
         (export never called layer_of(built.operators))
```

Through the executor, `layer` is always `layer_of(operators)` and `check_layer` enforces
declared-vs-ran, so this is unreachable by normal use. The gap is that `export` — a door whose
whole job is to be a gate — re-derives nothing and trusts an unauthenticated, caller-constructible
witness. Its consequence today is weak: the caller already chose `output_ref`, so it gains
nothing it could not get by reading the store directly; ClickHouse is out (scope); no downstream
consumer exists. It becomes real exactly where m4 §7 points — *"a later emitter is a consumer of
this function and inherits its door"* — and the door it inherits trusts a forgeable `.layer`.
This is the same class as RT-M4-01 and the D0235 findings: a public constructor lets a caller
forge the witness a guard trusts.

**Remedy:** one additive line — `layer_of(built.operators) is Layer.SERVE` alongside the existing
check. `export.py` is unfrozen (builder-landable); L4.10 (`test_l4_export.py`) is frozen but the
fix is *stricter*, not contradictory, so it needs no supersession — a rare finding whose remedy
is landable without an owner key or a new frozen law. Left for a session that is not this one, per
the D0104 norm, with the D0092 binding written then.

**Freeze/custody:** `src/tannen/export.py` unfrozen and uncustodied; `test_l4_export.py` frozen.

## RT-M4-04 — The RT-M3-01 code-address remedy hashes source text, which is blind to closure free variables. **Medium.**

RT-M3-01 (D0197, D0231) closed the "code named by string" hazard by addressing the code a
`DeltaNode` names by its **source text** — `_code_address` (`incremental.py:114`) hashes
`transform.source_text(fn)` (`inspect.getsource`, dedented, LF-normalised), and the map's
out-schema is folded in beside it. RT-M3-01 held M1's source-text hashing up as the gold standard
M3 had regressed from. **The gold standard is blind to a closure's captured environment.** Two
*named* closures with identical source but different captured values hash identically:

```
# a factory in a pipeline module, imported by `tannen run`:
def make(limit):
    def predicate(row):
        return row["x"] < limit
    return predicate

make(10)({"x": 50}) = False    make(99)({"x": 50}) = True     # they compute differently
source_text(make(10)) == source_text(make(99))                    → True
_code_address(make(10)) == _code_address(make(99))                → True  (601a3a00…)
```

Registered under one predicate name in two sessions — `register_predicate("risk", make(config.limit))`
— they mint one `DeltaNode` descriptor, so one `step_id`, while computing differently:

```
session 1 (limit=10) node.descriptor = sha256:adfd307d…
session 2 (limit=99) node.descriptor = sha256:adfd307d…       ← identical
```

That is RT-M3-01's exact hazard — two codes, one node, the trace serving the wrong answer with
`rebuilt=False` — reached through a plain **named** closure. A lambda is refused (`_code_address`
rejects `<lambda>`); a closure is not, and a closure-factory under a stable name is a realistic
pipeline shape. Reproduced across a persisted trace: `anti_join`/predicate nodes registered under
one name with different captures get the same `step_id`, and the second is served the first's
recorded output.

**Inherited from M1, not introduced by M4, and undocumented anywhere.** The mechanism is
`transform.source_text`, which M1's `@transform` uses identically for its `code_hash`
(`transform.py:76`); the collision is the same there. Grep of `transform.py`, `incremental.py`,
the specs and every prior red-team report finds no mention of the closure case — RT-M3-01's whole
argument was that source-text hashing is the correct model, and this is the hole in the model
itself. Frozen L4.23 never exercises it: its bodies have distinct source.

**A methodology note, because it nearly hid the finding.** The first reproduction, run from a
heredoc (`python - <<'PY'`), *falsely refuted* this: `inspect.getsource` cannot recover source for
code defined on stdin, so `_code_address` **raised** and refused the closure — the same protection
a lambda gets. That looked like a clean result. It is an artefact of the definition context: a
real pipeline is a `.py` file, where `getsource` succeeds and the collision is live. The
file-based reproduction above is the honest one. (The D0174-family lesson: a green — or here, a
refusing — result can be measuring the harness, not the code.)

**Severity Medium, not Critical:** it needs the closure-factory-under-a-stable-name pattern
(realistic but not the common path — the shipped catalogue is plain named functions), it is
inherited from M1's design rather than introduced by M4, and it serves a stale trace answer rather
than corrupting the store.

**Remedy — not builder-trivial.** `__closure__` cells cannot be reliably hashed (they may hold
unaddressable objects). The options are to refuse a closure the way a lambda is refused (safe but
blunt — it forbids a legitimate idiom), or to fold the canonical-encodable cell contents into the
address and refuse a closure whose cells are not encodable. It touches unfrozen `incremental.py`
**and** `transform.py` (the shared blind spot), and frozen L4.23 does not cover the case, so a
superseding law may be wanted — a decision record plus a future session, partly owner-adjacent.
A poison-fixture candidate is drafted below.

**Freeze/custody:** `incremental.py`, `transform.py` unfrozen and uncustodied; `test_l4_code_address.py`
(L4.23) frozen. Reported, not fixed (the D0104 norm).

## RT-M4-05 — Error classification is looser than the docstrings claim, all fail-closed. **Low.**

Two adjacent observations, neither a security break — every path fails closed — but each a place
where a docstring or a design note overstates what the code guarantees:

- **`tannen.r2`'s "every other failure is `R2Error`" is overstated.** `_send` (`r2.py:209`)
  maps `HTTPError`→status and `http.client.HTTPException`→`R2Error("outcome unknown")`, but
  `urllib.error.URLError` and `socket.timeout`/`TimeoutError` are `OSError` subclasses (verified)
  that propagate as **bare `OSError`**, not `R2Error`. Functionally fine — `tannen.oracles._write`
  catches `OSError` → `CaptureWriteFailed` — but a *timeout mid-PUT*, where whether the write
  landed is genuinely unknown, does not get the "outcome unknown" message that a mid-response
  `HTTPException` gets, and the module docstring claims a completeness it does not have.
- **A `tannen run` crash and a refusal share exit 1.** `_run` (`cli.py:91`) returns 1 on the four
  refusal classes with the class name on stderr, and lets everything else propagate — but an
  unhandled `ValueError` also exits 1 (CPython's default), with a traceback on stderr. D0237's
  stated design ("non-refusals propagate rather than collapse into an exit code that would read as
  a refusal") is achieved for *stderr* (traceback vs one-line `ClassName: msg`) but not for the
  *exit code*: a consumer keying on exit code alone cannot tell a refusal from an internal crash.
  L4.4 only asserts refusal ⇒ exit 1, which holds.

**Freeze/custody:** `r2.py`, `cli.py` unfrozen and uncustodied; both fixes builder-landable if the
owner judges them worth it. Reported as low because both fail closed.

## RT-M4-06 — Status audit: the RT-M3 remedies are closed and verified (RT-M3-01 with the closure residual of RT-M4-04); the infrastructure findings are unchanged; `required_tags` lags one boundary. **Informational.**

The RT-M1-06 / RT-M2-08 / RT-M3-06 pattern: what the prior passes left open, re-measured at
`3cac685`, plus an audit of D0231–D0244.

**Closed at M4, verified by re-attack — the three RT-M3 findings M4 was chartered to land:**

- **RT-M3-01** (code by name) — closed for names, **reopened for closures (RT-M4-04)**.
  `register_map` files a map under `_map_address(name, f, schema)` — the map's source address
  folded with its declared out-schema — so one body under one name with two schemas is two nodes
  (D0231). The predicate half was closed at D0197; the map's out-schema was the residue, and it is
  now in the descriptor. Confirmed. The catalogue's code is named functions, not lambdas
  (`_code_address` refuses a lambda, `:114`). But the remedy addresses code by its *source text*,
  which is blind to a closure's captured values — two named closures with one source and different
  captures are one node (RT-M4-04 above). So RT-M3-01's *name → code* gap is closed and its *code
  → behaviour* gap is not, at the source-text level M1 shares.
- **RT-M3-02** (the contagion set). RT-M3-02's remedy was "derive AND assert." Both landed:
  `binary_operators()`/`required_params()` are derived from `_ARITY`/`_REQUIRED` (D0232), and
  `_ALWAYS_REPLAYS` — still a hand-written set — is now **asserted against behaviour** by the
  unfrozen `tests/test_incremental.py::test_the_always_replays_set_is_derived_from_behaviour_not_from_memory`
  (it empties the set and checks that the operators that then diverge or raise are exactly its
  members), and its divergence is covered by frozen L4.24. So the finding is addressed; the residue
  is that the derive-and-assert is an *unfrozen* test (which RT-M3-02 itself noted), belt-and-braces
  with the frozen differential.
- **RT-M3-03** (operand roles). `advance` folds an `incroles/1` value naming which input held
  which operand role into a multi-input step's derivation inputs, so the two orders are two input
  values and therefore two derivations, with `derivation_id`'s formula untouched (D0232). `union`
  is not exempted (D0211 forbids writing down the interchangeable set). The swap pin
  `tests/test_incremental.py::test_a_binary_step_id_inherits_derivation_ids_order_insensitivity`
  is retired as an inline `@pytest.mark.xfail(strict=True, raises=AssertionError)` — a live
  assertion that goes red (XPASS) if the remedy is reverted, not a deletion. Confirmed.
- **RT-M3-04** (oracle-shadow). Closed two ways at once: every M4 law file binds its frozen helper
  through `tests/laws/m4/_frozen_bind.py` (executes the bytes by file location, never reads
  `sys.modules`), and `src/tannen/laws/plugin.py:_oracle_shadow_problem` now compares the code a
